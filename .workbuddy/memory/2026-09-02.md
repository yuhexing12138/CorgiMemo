## 重建灵感编辑页撤销栈为方案A（自建 Command 命令栈 + 库内 history，两套历史隔离）

### 决策来源
用户给出方案A方案全文：底层自维护 `List<Block>`（TextBlock/ImageBlock）；撤销栈只存操作增量 Command，不存全量快照；块级 Command（增删/排序/图片块属性）与块内富文本（复用 compose-rich-editor 自带 history，不进全局栈）两套历史隔离；五大坑点（焦点判断/Image 不存 Bitmap/拖拽手指抬起才压栈/旋转放 VM/复合操作）。

### 核心架构
- **全局命令栈** `undoCommands`/`redoCommands`（`ArrayDeque<BodyBlocksCommand>`）+ **块内库自带 history**，统一调度入口 `undo()`/`redo()`：聚焦块（未聚焦回退首块）`history.canUndo` 非空 → 先回退块内文字；空则走命令栈。
- Command 体系（新增于 BodyBlocksEditor.kt 文件头）：`BlockSpec`（TextSpec/ImageSpec，**绝不持 Bitmap**——坑点2）/`FocusSpec`/`BodyBlocksCommand`（apply=revert）/`ReplaceBlocksCommand`（区间替换，覆盖插图拆块/Enter拆块/粘贴归一化/退格合并/删图/首空块删除全部形态）/`MoveBlockCommand`/`UpdateImageBlockCommand`（图片属性模板，三件套扩展点，当前无调用方）/`CompositeCommand`（批量插图 = 一个撤销单位——坑点5）。
- 落盘原语：`replaceBlockRange`/`rebuildBlock`（id 复用保焦点稳定）/`drainBlockHistory`（revert 前把产物块库内 history 撤到底，避免静默丢弃用户文字）/`locateRangeStart`（id 防御定位）。

### 五大坑点落地
1. 焦点判断：`undo()` 入口先查聚焦块 `history.canUndo`，空才 `undoBlocks()`。Ctrl+Z/Ctrl+Shift+Z/Ctrl+Y 由 BlockTextItem.onPreviewKeyEvent 拦截调同一入口（`undoBehavior = UndoBehavior.Disabled` 保持，避免库绕过调度）。
2. ImageBlock 绝不持 Bitmap：`BlockSpec.ImageSpec` 只存 `path: String`。
3. 拖拽压栈：`BlocksReorderableColumn.onSettle`（手指抬起落定）才回调 `moveBlock` → 一步拖拽一条 `MoveBlockCommand`。
4. 旋转：`BodyBlocksController` 整体由 `InspirationEditViewModel` 持有（不再 UI `remember`）；新增 `hasInitialized` 标志随 controller 存活，**旋转后不重跑 initialize**（避免清空命令栈）；trigger 注册一并移入 VM。
5. 复合操作：`CompositeCommand`（apply 顺序、revert 逆序）+ `insertImagesAtFocused` 批量插图 = 一个撤销单位。

### 关键语义
- **新编辑清全局 redo**：observer 检测非重放（`replaying=false`）的 markdown 变化 → `clearGlobalRedo()`。保证"redo 可达 ⇒ 各块当前内容 == 上次全局操作结束时的内容"，命令重放记录值安全。
- **replaying 标志**：Command 重放与块内 history undo/redo 期间置 true，observer 跳过结构检测（\n拆块/退格合并）与清 redo，保留 ZWSP 维护。
- **drain 语义**：`ReplaceBlocksCommand.revert` 删除产物块前先 drain 它们的库内 history（让文字逐步回退可见）。
- **ZWSP 剥离**：`blockMarkdown()` 统一剥 ZWSP 作为 Command 载荷出口，重建走 `createTextBlock`（空 markdown → ZWSP 预置）。

## 修复「撤销图片后光标跑到'一'左边」的焦点竞态
- 现象（紧接上一条修复后出现）：输入"一""二"→ 中间插照片 → 撤销一次图片消失（剩一二），但光标落在"一"左边（offset 0），正确应在"一"和"二"之间（offset 1）。上一条 fix 前光标是正确的，说明 `restoreBlockRange` 新路径触发了焦点时序问题。
- 根因：`pendingFocusId` 与 `pendingFocusOffset` 是**两个独立 `mutableStateOf`**；`applyFocusAndCursor` 在 undo 回调快照里同步写两者，而 `BlockTextItem` 的 `LaunchedEffect(controller.pendingFocusId)` 以 id 为 key 重发射、再读 `pendingFocusOffset`——两条独立状态在快照边界上可能读到过期 offset（旧交互残留的 0），把已正确设好的光标（offset 1）覆盖成 0。`restoreBlockRange` 复用带 RichTextState 历史的旧块对象恰好放大了该竞态。
- 修复：把两个独立状态合并为单一 `internal var pendingFocus by mutableStateOf<FocusSpec?>(null)`（直接复用已有的 `FocusSpec(data class, blockId+offset)` 作原子打包）。`applyFocusAndCursor` 改为 `pendingFocus = FocusSpec(target.id, offset)`；`currentFocusSpec` 读 `pendingFocus?.blockId`；`LaunchedEffect(controller.pendingFocus)` 在 key 整体变化时一次性读到 id+offset 一致的同一份快照，从根上消除竞态。`focusFirstTextBlock()` 经 `applyFocusAndCursor(firstText, 0)` 仍走同一出口，不受影响。
- 验证点：id 变化与 offset 是同一次写入，LaunchedEffect 重发射时读到的 offset 必与触发它的 id 同源；光标应稳定落在"一""二"之间。本机未编译（用户约定不自动 gradle 构建）。

## 修复「空白块保存后重新进入消失」
- **现象**：编辑态创建了空白块（段落间留空行），保存后再进入编辑页，空白块全部消失，只剩有内容的块。
- **根因**：空白块在序列化与重建两侧都被丢弃。
  - 保存侧 `BodyBlocksEditor.kt` `toMarkdown()`：对 Text 块剥 image 段后 `.filter { it.isNotBlank() }` 把空段丢弃；空块经 `.ifEmpty { null }` 变 null 被 `mapNotNull` 跳过；外层 `.filter { it.isNotBlank() }` 再丢空段 → 空白块不进 markdown。
  - 加载侧 `initialize()`：`seg.md.split("\n\n")` 后 `if (trimmed.isNotBlank()) blocks += createTextBlock(trimmed)` 把空段落丢弃 → 块列表无空块。
- **修复（两侧对称保留空白块）**：
  - `toMarkdown()`：`mapNotNull`→`map`，去掉块内 `.filter { it.isNotBlank() }` 与 `.ifEmpty { null }`、去掉外层 `.filter { it.isNotBlank() }`；空块序列化为空段 `""`，块间 `\n\n` 连接（空块对应一个空段）。
  - `initialize()`：去掉 `if (trimmed.isNotBlank())`，空白段统一 `blocks += createTextBlock(trimmed)`；`trimmed` 为空串时 `createTextBlock("")` 预置 ZWSP 退格锚点，与编辑态空块语义一致。
  - 纯文本段落间空块 round-trip 精确对称：`[t1,空,t2]` ↔ `t1\n\n\n\nt2` ↔ `[t1,空,t2]`。
- **已知限制（边界 case，非数据丢失）**：图片块 `ImageSeg` 与空白块严格相邻时，因 markdown 用 `\n\n` 分隔、空块内容为空，解析侧会把「空块↔图片」之间的分隔符误判为一个额外空段，重新进入可能在边界多出一个空块（不会消失，仅可能冗余）。彻底方案是把空块用显式非空占位符（如 NBSP `\u00A0`）序列化，可作为后续优化。**（已于『图片相邻空块彻底修复（NBSP 占位符）』解决，见下条）**
- **自检**：`map`/`mapNotNull` 切换无新类型；`BodyBlock`/`MdSegment`/`ZWSP`/`createTextBlock`/`parseMarkdownSegments` 均已在文件内，无新增 import。未编译（用户约定不自动 gradle 构建）。待用户决定是否 git 提交（仅 BodyBlocksEditor.kt）。

## 图片相邻空块彻底修复（NBSP 占位符）——补上一条的边界 case
- **背景**：上一条「对称保留空白块」修复后，纯文本空块 round-trip 正常，但**图片相邻的空块仍会在重新进入时多/少空块**。根因比预期更深：markdown 用 `\n\n` 同时作「块间分隔」与「文本块内段落分隔」，图片块 `![](p)` 前后需 `\n\n` 才能与文本分隔；旧代码靠 `if (trimmed.isNotBlank())` 丢弃**所有**空段（包括图片边界分隔符）才没暴露歧义，上一条去掉该过滤后，图片边界的「段间空段」现在也被建成空白块——这是上一条修复新引入的回归，非历史遗留。
- **彻底方案（两侧配合）**：
  - 序列化侧 `toMarkdown()`：空块（`raw.isEmpty()`，`raw` 为剥 ZWSP 后内容）输出 `EMPTY_BLOCK_PLACEHOLDER = "\u00A0"`（NBSP），让该段在 markdown 中**非空**，块边界无歧义；非空块逻辑不变。
  - 重建侧 `initialize()`：`parseMarkdownSegments(markdown)` 结果带索引遍历（`forEachIndexed`），对每段 TextSeg 计算 `prevIsImage`/`nextIsImage`；按 `\n\n` 拆段后，**紧贴图片块的边界空段**（`pIdx==0 && prevIsImage` 或 `pIdx==last && nextIsImage` 且 `trimmed.isEmpty()`）识别为分隔符 `return` 跳过——只丢图片边界那一个空段，段内真实多段与独立空块都保留；其余空白段（空串 / NBSP 占位符）一律 `createTextBlock("")` 重建为空白块。
  - 新增常量 `private const val EMPTY_BLOCK_PLACEHOLDER = "\u00A0"`（ZWSP 常量旁，带文档注释说明占位动机）。
- **round-trip 验证（已逐场景推演，未编译）**：
  - `[t1,空,t2]` ↔ `t1\n\n\u00A0\n\nt2` ↔ `[t1,空,t2]`（纯文本空块精确）
  - `[t1,空,img]` ↔ `[t1,空,img]`；`[t1,img,t2]` ↔ `[t1,img,t2]`（图片相邻空块与无空块均不增删）
  - `[t1,空,img,空,t2]` ↔ 5 块精确；`[img1,空,img2]` ↔ 中间空块保留、边界空段丢；`[img,t1]`/`[t1,img]` 边界正常
  - 纯空文档 `""` ↔ `\u00A0` ↔ 1 空白块（ensureTextBlock 不重复加）
- **自检**：`EMPTY_BLOCK_PLACEHOLDER`/`ZWSP`/`MdSegment`/`BodyBlock`/`newBodyBlockId`/`createTextBlock`/`ensureTextBlock`/`clearCommandStacks` 均在文件内；`segs.lastIndex`/`paras.lastIndex` 为 List 内置属性；无新增 import。未编译（用户约定不自动 gradle 构建）。待用户决定是否 git 提交（仅 BodyBlocksEditor.kt）。
