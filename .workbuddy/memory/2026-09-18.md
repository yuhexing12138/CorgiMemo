## 留白间隙收紧 6 → 0（v1.11.2）

用户要求「改小到 0（再挤一点）」。

**改动**：`SIDE_MENU_GUTTER_GAP` 6 → 0，于是 `padding-inline-start = 24 + 0 = 24px`，
**⋮⋮ 手柄紧贴编辑区左边缘**（手柄左边缘 = 24 − 24 = 0）。

**先验证了安全性再动手**（这是关键）：
- 嵌套列表竖线在 `left: -20px` → 需 20px，24 > 20 ✓
- toggle 添加按钮 `margin-left: 22px` → 需 22px，24 > 22 ✓
- → **两者仍不被裁**，所以收紧到 0 无副作用。

⚠️ **24px 是该值的下限**：手柄本身已占 24px，而上面两个内置控件各需 20/22px，
故间隙只能为 0、不能为负。这条已写进 editor.css、MEMORY.md 与方案文档。

**效果**：内容可用宽度 `W − 30` → `W − 24`（再净增 6px）。
对比最初官方 `W − 108`，累计净增 **84px**。

**位置对照**（手柄距编辑区左边缘）：

| v1.11 | 24px | 30px | 6px |
| **v1.11.2（当前）** | 24px | 24px | **0px** |

> 有趣的是 v1.11 的 6px 与官方完全一致（因为间隙常量就是照官方「48+6=54」里的 6 取的），
> 所以上一轮真机上会看到"视觉位置没变、内容变宽了"。本轮收紧后手柄才真正贴边。

## 内容区留白改为左右对称（v1.11.3）

用户提问：文本左右边缘到屏幕的距离各是多少？并要求把右侧设成与左侧相等。

### 核算结果（改动前）

| 侧 | 链路 | 合计 |
|---|---|---|
| 左 | 宿主内容区 Column `padding(horizontal = 8.dp)` + `.editor-page` 0 + `.bn-root` 0 + `.bn-editor` `padding-inline-start: 24px` | **32dp** |
| 右 | 宿主 8dp + `.editor-page` 0 + `.bn-root` 0 + `.bn-editor` `padding-inline-end: 0` | **8dp** |

差 24dp。**相差的正好是 v1.11.2 让右侧归零的那 24px**。

### 改动

`.bn-editor` 的 padding 由 start/end 分开写改为**左右同值**：

```css
.bn-editor {
  padding-inline: var(--bn-editor-gutter, 24px) !important;
}
```

于是左右均 = 8dp（宿主）+ 24px = **32dp** ✓ 对称。

**顺带把 CSS 变量改名** `--bn-side-menu-gutter` → **`--bn-editor-gutter`**：
它现在同时控制左右两侧，而右侧与"侧边菜单"毫无关系，旧名会误导。
同步更新 EditorApp.tsx / editor.css / bridge-protocol.md / 方案文档 / MEMORY.md。

**新增常量** `EDITOR_CONTENT_GUTTER = SIDE_MENU_HANDLE_WIDTH + SIDE_MENU_GUTTER_GAP`：
- `SIDE_MENU_HANDLE_WIDTH = 24`（手柄物理宽度，事实）
- `SIDE_MENU_GUTTER_GAP = 0`（手柄与文本间隙）
- 两者相加 = 内容留白 24

⚠️ 已在 KDoc 里写明**该值同时受两个语义支配**：左侧"容纳手柄"（硬约束）、
右侧"视觉对称"（用户要求）。若日后冲突（想单独调右侧），
拆成 `-start` / `-end` 两个变量即可。

### 效果

| | 内容可用宽度 | 左/右留白 |
|---|---|---|
| 官方默认 | W − 108 | 54 / 54（对称但都过大） |
| v1.11 | W − 30 | 30 / 0 |
| v1.11.2 | W − 24 | 24 / 0（最满，但不对称） |
| **v1.11.3（当前）** | **W − 48** | **24 / 24（对称）** |

相对官方仍净增 60px；相比 v1.11.2 **主动让出右侧 24px** 换取视觉对称。

### 校验

- `npm run typecheck` exit 0 ✅
- 产物重建 1,884.50 kB ✅
- 关键字核验：`--bn-editor-gutter` ×2、`--bn-side-menu-gutter` **×0**（旧名已清）、
  `.bn-editor{padding-inline:var(--bn-editor-gutter, 24px)!important}` ✅
  另注意产物里还有一条 `.bn-editor{padding:0}`（来自 BlockNote 官方 CSS），
  被我们的 `!important` 覆盖，无影响。

## 排查「右边边距看着大」+ 修复背景色变量被覆盖（v1.11.4）

### 用户问题：为什么感觉右边边距大？

**没有目测、没有推算，直接逐像素分析用户上传的截图**（pillow 逐行/逐列扫描深色像素）：

| 元素 | 左边缘 | 右边缘 | 左距 | 右距 |
|---|---|---|---|---|
| 正文行 | 73–88px | 757–771px | 77px | 94px |
| 标题行 | 21px | — | 8.7dp | — |
| 日期行 | 20px | — | 8.3dp | — |

**结论**：右侧确实多 ~17px。但 **CSS padding 是严格对称的**（已用产物逐条核过
`.bn-editor{padding-inline:var(--bn-editor-gutter, 24px)!important}` 唯一生效，
官方 `.bn-editor{padding:0}` 无 `!important` 且在前 → 不生效）。

**真因**：这行文字**没有填满可用宽度**（差约 7dp）。左对齐文本的剩余空间必然落在右侧，
所以视觉空隙 = 32dp（对称内边距）+ 7dp（未填满）= 39dp。

**交叉验证**：由正文左距 77px ↔ 理论值 32dp 反推出 屏幕 ≈ 360dp、密度 2.4，
与整屏 864px 自洽 ✓ —— 这让结论可信度大幅提升。

> **概念澄清**（值得记住）：**"容器内边距对称" ≠ "文字两侧视觉空隙对称"**。
> 只要文字不满一行，后者必然不对称。用户要的前者已经达成。

### 顺带发现的真 bug：`.bn-editor` 背景其实是纯白

分析截图时发现正文位置有 **830×128 的纯白 `(255,255,255)`** 矩形，而主题背景是
暖米色 `(255,251,245)`。它无圆角、宽度等于 WebView 宽、高度等于内容高 → 就是 `.bn-editor` 自身。

**根因**：BlockNote 官方在 **`.bn-root`** 上定义了整套颜色变量
（`--bn-colors-editor-background: #fff`，暗色分支 `#1f1f1f`），
而 v1.9 把同名变量设在 `<html>` 上 → **CSS 变量就近取值**，`.bn-root` 更近、胜出。
我们 CSS 里那个 `var(--bn-colors-editor-background, var(--editor-bg))` 的 fallback
**永远不执行**（前一变量总有值）。

**为何长期没发现**：`.bn-editor` 高度只由内容决定，白条又被 `html/body` 与 `.editor-page`
的米色包围，容易被当成"输入区域的强调"。且 v1.9 的验证只做了「产物含 #FFFBF5 字符串」计数。

**修复（v1.11.4，双保险）**：
- CSS：`.bn-root, .bn-root[data-color-scheme="dark"] { --bn-colors-editor-background: var(--editor-bg, #ffffff) !important }`
  （**必须含暗色分支**，官方对暗色单独定义过）
- JS：改为 `document.querySelectorAll(".bn-root").forEach(el => el.style.setProperty(k, v, "important"))`
  （不再写无效的 `<html>`）

### padding 的决策过程（最终未改）

用户先要求「去掉两侧 padding」，但 **`.bn-editor` 左侧那 24px 是手柄的落脚区**
（手柄左边缘 = padding-left − 24），去掉则手柄完全出视口 —— 即 v1.9 的回归。
说明冲突后用户改选「去掉宿主 8dp」（无副作用）。

但实施前实测发现：**那 8dp 是作用在整个内容区上的，标题/日期行只有它没有编辑器的 24px**
（标题 8.7dp、正文 30.3dp，本来就差 24dp 未对齐）。去掉 8dp 会让标题**贴到屏幕边缘 0dp**。
告知后用户选择**不改了** → 本轮 padding 零改动。

> 副产品：量化了「标题 8dp / 正文 32dp 不对齐」这个**既有**不一致，已记入文档待议。

## 拖拽手柄删除 + 块移动改按钮化（v1.11.5）

### 用户问题：按住 ⋮⋮ 为什么无法拖拽？

**排查结论：平台级限制，不是我们的 bug，且无法绕过。**

证据链（三层）：
1. **BlockNote 源码**（`SideMenu.ts` 802 行）：块拖拽**纯用 HTML5 原生 Drag & Drop**
   （`draggable` + `dragstart`/`dragover`/`drop`/`dragend` + `dataTransfer`），
   **零 touch / pointer 事件处理**——没有任何触摸兜底。
2. **平台规范**：W3C 把 drag 事件定义为**鼠标驱动**行为。Android WebView、
   Chrome for Android、iOS Safari 在触摸下**根本不派发这些事件**
   （`draggable="true"` 与否无关，`dataTransfer` 在触摸上下文也是空操作）。
   多个来源一致：这不是兼容性问题，是浏览器没实现。
3. **旁证**：OpenProject 团队评估 BlockNote 的文档明确记录
   *"Blocknote has some features that have to be disabled in mobile (drag-and-drop, toolbar)"*。

**重要推论**：v1.11 保留手柄的理由（"它承担拖拽重排"）**在 Android 上根本不成立**。
我们为一个不可用的功能保留了 UI + 占用了左侧 24px，还让用户困惑了一轮
（之前没暴露是因为手柄本身被裁在屏幕外看不见）。

### 决策（用户）：删除手柄 + 「上移/下移」按钮替代

排查中确认 BlockNote 提供程序化 API：
`editor.moveBlocksUp(blockIdentifier?)` / `moveBlocksDown(blockIdentifier?)`。

| 设计决策 | 理由 |
|---|---|
| 不置灰 | BlockNote 内部 `getMoveUpPlacement` 到顶返回 undefined 直接 return，是**安全 no-op**；但 API 未暴露"能否移动"的判定，点了没反应即代表已在边界 |
| 不关菜单 | 便于连续点击把块一路移上去（与色板行的"保持打开"一致） |
| 不传参 | BlockNote 会取**选区首/末块**或**光标块**，天然支持多选一起移动与嵌套块 |

### 改动清单

**JS 侧**（EditorApp.tsx / bridge.ts / editor.css）：
- 删除：`SIDE_MENU_HANDLE_WIDTH` / `SIDE_MENU_GUTTER_GAP` / `NoDragHandleMenu` /
  `DragHandleOnlySideMenu` / `<SideMenuController>` / 相关 import（含 `type FC`）
- `EDITOR_CONTENT_GUTTER` = 24 → **20**（不再是"手柄宽+间隙"，语义变为
  "嵌套列表缩进线的下限"）；CSS fallback 同步 24 → 20
- 新增下行命令 `moveBlockUp` / `moveBlockDown`（handler 直接调 `ed.moveBlocksUp/Down()`）
- `sideMenu={false}` 保留，`<SideMenuController>` 移除

**Kotlin 侧**：
- controller：新增 `moveBlockUp()` / `moveBlockDown()`
- 工具栏：`BlockOpsMenuButton` 增「上移 / 下移」两个菜单项（紧跟"删除块"，
  因为同样与块的位置相关；参数透传三层：BottomBar → Screen → controller）
