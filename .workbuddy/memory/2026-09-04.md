## 第三轮：连续换字 ~25 款后 OOM 闪退（实测 meminfo 数据）
- 实测两份快照（mem_before/after.txt，UTF-16 编码需 iconv 转 UTF-8）：连切约 25 款字体后 TOTAL PSS 232975→462197（+229MB）。
- **关键结论**：增长几乎全在 **Dalvik(Java) Heap**（+203MB，Heap Size 71k→350k ×4.9，GC 收不回=真泄漏）；**Native Heap 仅 +8.8MB**（隔离 resolver + clearCache 的硬约束对 native 生效，常驻字体被压在 2 款内）。
- 代码排查：FontPreviewEngine（池 2/3 + 位图 LruCache 32，位图每张≈60KB）、FontWeightProbe.cache（无界 LinkedHashMap 但只存极小 Set<Int>）、应用流程（onCjkFontSelected→ContentFontManager.setCjkFont→clearTypefaces，无意外持有）——**全部有界，均非 200MB 主因**。
- 判定：200MB Java 持有链在 Compose 字体解析路径内部（最疑每次换字 new FontFamilyResolverImpl 的重建震荡 + 重组/异步边界未释放），纯读代码无法精确定位，需堆转储。

## 第四轮：堆转储定位根因 + Option A 根治
- 用户交付 `heap.hprof`。先试官方 `hprof` PyPI 库（开代理后 SSL/404 均失败，PyPI 上无此包）→ 改为修复自写流式解析器 `scripts/hprof_histogram.py`。
- **解析器关键修复**：CLASS_DUMP 静态字段名是 **idSize 字节（非 u2）**，原代码 `i += 2` 每字段少读 2 字节、跨字段累积偏移直至读取长度爆表（曾读到 34 亿长度的 OBJECT_ARRAY）；修正为 `i += idSize` 后直方图可信。另加 INSTANCE/数组长度合理性兜底 + 段级 abandon/resync（替代激进「扫到任意 tag」再对齐）。配套 `hprof_diag.py`（佐证 0xff 是 ART 无体子记录）、`hprof_drift.py`（首处不可能 size 即退，定位漂移点）、`hprof_referrers.py`（≥3MB byte[] 持有者扫描，背景运行补充）。
- **根因（堆转储实证）**：`byte[]` 总量 ≈ 502MB（502258410 个、最大项均 13~18MB 成组出现，恰与 10 款 CJK + 3 款 Latin 字体文件尺寸吻合）；`Typeface` 仅 133 个（6384B，**非 Typeface 泄漏**）。泄漏来自 Compose 解析 `Font(resId)`（ResourceFont）路径：`AndroidFontLoader`→`TypefaceCompat.createFromResources`→`Typeface.createFromInputStream` **把整份字体文件读进 Java 堆 byte[]**；每个字体被 chrome resolver / content resolver / 框架字体缓存各留 1 份 → 常驻 3~4 份。既有 `FontResolverPolicy.clearCache()`（TypefaceCompat.clearCache + emptyCacheFontFamilyResolver）只清 Typeface 对象，**清不掉**文件 byte[]，故无效。
