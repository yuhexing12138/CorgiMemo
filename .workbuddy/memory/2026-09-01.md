## 用户提出的后续需求：图片裁剪 / 缩放 / 备注

- 用户明确后续要在灵感编辑页对插入图片做**裁剪、缩放、备注**。这三项需求改变了路线权衡，结论已补充进 v2 报告的决策依据。
- 核心判断：这三项把图片语义从"行内字符"升级为"结构化媒体对象"；**路线 2 与路线 4 的差距因此大幅缩小**——
  - 裁剪：两边完全一样（都是开原生裁剪页 → 回传新文件 → 替换节点 src）。
  - 缩放：路线 4 更直接（图片块是 Composable，宽度即 state，无需桥接）；路线 2 需 JS 上报 `getBoundingClientRect()` + 坐标换算后画原生拖拽把手。
  - 备注：路线 4 更直接（图下放原生 TextField）；路线 2 需 `figure+figcaption` 块节点（会破坏 inline 语义）或节点 `note` 属性 + 原生弹窗。
- **路线 2 剩下的独有优势收敛为唯一一条：图片能否插在句子中间。** 这是现在唯一该问的产品问题。
- 建议：备注若用 `figcaption` 会让 figure 变成块节点，与 inline 冲突 → 若坚持 inline，备注必须走"节点属性 + 原生底部弹窗"。
- 裁剪**不要覆盖原图**：应存 `originalPath` + `cropRect`，否则"重新裁剪"无法还原。
- 两项待定（越早定越好，后期改要迁数据）：① 备注是否参与搜索/导出（决定它是节点属性还是文档内文本）；② 属性存文档 JSON 节点 attrs 还是 Room 加列。

### 概念澄清：块级（图文交错）vs 行内（句子中间插图）
- 块级 = 图片与段落平级，前后强制换行，只能放在段落之间；行内 = 图片与文字平级，本质是超大号字符，文字在它左右继续排，前后仍属同一段。
- 对照（Word 类比）：行内 = Word「嵌入型」；块级 = 独占一整块（移动端笔记 App 主流做法）；第三类「浮动/四周型环绕」移动端基本不做。
- 主流笔记产品（微信公众号、Notion、飞书、印象笔记、Obsidian、Bear）**都是块级**。不要被"看起来图文混排"误导——图在两段文字之间仍是块级。
- **关键实践判断**：行内插图真正好用的只有小尺寸元素（表情、图标、行内公式、小徽章）。大照片做行内会把句子劈成上下两截，阅读体验反而变差。本项目场景是"往笔记里插照片"（通常是大图），因此**默认应走块级（路线 4）**。
- 图注（备注）天然是块级语义：块级模型下图注就是跟随图片块的文字区；行内模式下无处安放（即 figcaption 与 inline 的冲突）。
- 快速判定法："我买了 ___ 三个苹果"——若要求空格处插图且前后文字同处一行 → 行内；若"图放在这句话上面或下面都行" → 块级。

## 图片插入 bug 修复（联调反馈，14:25）

- 症状：插入图片后"图片后"的"后"字丢失、第二块变成"▢图片"（占位符 ▢ 跑到第二文本段）。
- 根因：`insertImageAtFocused` 用了 `insertMarkdownAfterSelection("![](path)")` 这条**有缺陷**的路径。
  - 库的 `RichTextStateMarkdownParser.encode("![](path)")` 处理空 alt 时只调用一次 `onText("")` 并立刻 early-return，**跳过了 `currentRichSpan.text = InlineContentPlaceholder`（▢）的赋值**——Image span 的 text 字段保持空。
  - Image span 空 text 但 `richSpanStyle.isAtomic = true` → `isEmpty()` 返回 false（`isEmpty()` = text.isEmpty && childrenEmpty && !atomic），所以不会被 onCloseNode 移除。
  - 后果：toMarkdown 输出看似正常，但因 image span 的 text 长度计算与 cursor 偏移映射在拆块 + 重解析链路里错位，第二个 TextSeg 内容错位。
- 正确做法：调用库专用的 `RichTextState.insertImage(model = path)`（对应 `performInsertImage`，`RichTextState.kt:387`）。它**手工**构造 Image 段并正确赋 `text = ▢`，再把原段落拆成 [前半段, Image段, 后半段]。后续 `toMarkdown()` → `parseMarkdownSegments` 链路正常，段间 `\n` 由 `split("\n\n") + trim('\n')` 安全处理。
- 修改：`BodyBlocksEditor.kt:231 insertImageAtFocused` 换 API；`InspirationEditScreen.kt:150-174` 路线 2 残留注释（介绍 ▢/U+FFFD/inline-content 占位）整段替换为简短说明。

## 光标偏移 bug 修复（联调反馈，15:02）

- 症状：插图后光标落在"图片后"的"图片"和"后"之间（offset 2），预期在最前端（offset 0）。
- 根因：`focusAtOffset` 的 `consumed` 累计用的是**块自身长度**（3+1+3），但 `cursorOffset` 来自**库 raw text 坐标系**——相邻段落之间有 1 个连接空格（`updateRichParagraphList` 的 `append(' ')`），占位符 ▢ 又占 1 字符。差值正好 2 个段间空格：cursorOffset=6 被算成 6-4=2。
- 修复：每跨过一个块 `consumed += len + 1`（+1 = 段间连接空格）；求出偏移再 `coerceIn(0, len)` 兜住空块边界（尾插时光标落空 Text 块会算出 -1）。
- 注意区分坐标系：`normalizeBlockParagraphs` 里的 `consumed += len + 1` 是**块内 `\n` 坐标**（行间 = `\n` 字符），与段间空格不是一回事，不需要改。
- 提交：`ad10b152`（▢ bug）+ `6a8344fc`（光标偏移）。

## 拖拽手柄错位修复（联调反馈，15:25）

- 症状：进入灵感编辑页后，左侧拖拽竖条与编辑行错位——多行块的手柄浮到垂直中间（不是对齐第一行文本），初始空块（160dp 高度）手柄被推到 ~80dp 中心高度，离占位符第一行也很远。
- 根因（上一轮块间距修复的连带副作用）：把 `Row(verticalAlignment = Alignment.Top)` 改成 `Alignment.CenterVertically` 是为了让单行块的把手垂直居中，但 `CenterVertically` 是按整 Row 高度居中——对多行块 / 高空块都偏位。
- 修复：`BlockTextItem` 和 `BlockImageItem` 两处的 Row 都改回 `Alignment.Top`。手柄 `heightIn(min = 24.dp)` 决定最小尺寸，内容（编辑器或图片）决定 Row 高度，手柄永远坐在左上角——这是 Notion / Linear / Capacities 等块编辑器的把手标准对齐方式，能形成左侧竖列。
- 同步修正 `BlockTextItem` 上方注释：原注释写「verticalAlignment = CenterVertically 由文本块决定整行高度」是错误因果——居中只决定子元素位置，不决定 Row 高度（Row 高度由 `heightIn(min)` 最大的子决定）。新注释明确四点：① 手柄只留 24dp 最小高坐在左上角；② Row 用 Top 保证多行也不浮中间；③ 编辑器 minHeight=0 + contentPadding=0 让块高 = 行数×行距；④ 未来改 lineHeight 同时作用于块内/块间。
- 提交：`27304bd0`。

## 两类撤销互斥实现（联调反馈，17:16）

- 需求：连续打字 → 撤销 → 逐字回退，且不触发块级快照；两类撤销互斥。
- 根因（两条独立逻辑都没实现）：
  1. **库的合并窗口默认 500ms**：`RichTextHistory.coalesceWindowMs = 500L`（`RichTextState.kt:81`），连打"abc"在 500ms 内被合并成 1 个 undo group，撤销一次全删——不是"逐字回退"。
  2. **结构变更没清文本 history**：`pushBlockSnapshot` 只压块快照，没清掉 Text 块的 `state.history`。后果：用户在 Text("12") 打 "x" → 插图 → 撤销块级 → 回到 Text("12") 时，"x" 的 history 还残留 → 还能继续撤销到 "x之前"——**两类没真正互斥**。
- 修复：
  - `createTextBlock`：`state.history.coalesceWindowMs = 0L` 禁用合并，每个字符独立 undo group
  - `pushBlockSnapshot`：压快照后 `blocks.forEach { (it as? BodyBlock.Text)?.state?.history?.clear() }`，清空所有 Text 块的文本 history
- **API 来源**：库有 `RichTextHistory.clear()` 方法（`RichTextHistory.kt:79`），无需改库。
- **副作用**：
  - 合并窗口改 0 后，每个 keystroke 都是独立 undo group，history 容量增长变快（默认 100 个 group），考虑后续按需调高 historyLimit 或重新引入"按字符类型/时间合并"策略
  - 结构变更清 history 后，用户不能再"先打字再插图再撤销回来字还在"——文本/结构真互斥（与设计意图一致）
- 提交：`cd6f63fc`。

  5. 退格合并/空块删除的压栈统一到 onBackspaceAtStart 入口（observer 对这两种差分跳过压栈——硬键盘路径 text 未变 observer 不触发，入口压栈才能双路径覆盖）
  6. **normalizeBlockParagraphs 不再内部压栈**：observer 已压"变化前"；若内部再压会压到"含\n中间态"，撤销恢复它 → observer 又检测 \n → 死循环
  7. `RichTextEditor(undoBehavior = Disabled)` 禁库内 Ctrl+Z（避免与统一栈并存）；页面撤销/重做按钮只走统一栈
- 光标链路：快照 cursorOffset（有效坐标）+ restoreCursor → 撤销插图后光标回插图前位置（1|2）✓
- 库的 inlineImageRendering 开关保留（防御性：粘贴含图 markdown 进块内时覆盖层不画图）。
- 已知取舍：中文 IME 组合结束后压的快照"变化前"是组合最后中间态（撤销先见拼音残迹），后续可优化。

## 块首点击插图不拆块修复（19:32 联调截图）

- 症状：批量插入两张图，结果 `[Image(A), Image(B), Text("12")]`——"12"未被拆开、整体留在图片后；用户截图显示光标在"12"左侧最前端（offset 0），描述说"光标在 1 和 2 之间"。
- 根因：用户主观认为光标在"1 和 2"字符之间（offset 1），但库 IME 调整器或点击偏一像素导致 `state.selection.start = 0`（块首）。`RichTextState.insertImage` 在 offset 0 处把"12"整段切成 `[空段, 图段, "12"]`，replaceBlockWithParsed 重解析后"12"作为整体 Text 块保留，"1"和"2"从不被拆开（它们在同一个 Text 块内从未分开过）。
- 修复：`BodyBlocksController.insertOneImageInternal` 在 `state.insertImage` 前，若检测到 `selection.collapsed && selection.start == 0 && 块非空`，**自动把 selection 调到 `TextRange(1)`**（首字符后）——把"在 1 和 2 之间"的主观意图变成现实的插入位置。
- 副作用：用户真的想在块首插图时（罕见），图会落到首字符后。常见做法是先按 Enter 拆块再插图，影响可接受。

## 块首点击插图根因修复（19:38，第二次迭代）

- 用户的反馈：上次"自动跳过块首"的修改方向错了。重新分析根因。

  - `state.toMarkdown(TextRange)` 处理单段/多段/含 token/含 list/含 heading 都能正确分隔
- 行为：按用户真实光标位置插入图片
