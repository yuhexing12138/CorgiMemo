### 关键环境坑：代理导致 GitHub 不可达（重要，已记入用户级记忆）
- 本机环境变量注入了 `http_proxy/https_proxy = http://127.0.0.1:56997`，该代理对 `github.com` 的 CONNECT 隧道返回 **502**，`git clone` 直接失败：`fatal: unable to access ... CONNECT tunnel failed, response 502`。
- WebFetch / api.github.com 走另一通道不受影响，故容易误判"网络正常"。
- **解法**：克隆时临时剥离代理变量即可直连：
  `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY git clone --depth=1 <url>`
- 同理适用于 `git pull` / `git ls-remote` / curl 等所有访问 github.com 的命令。

### 数据分析踩坑（复用价值高）
1. **`subfamilyName` 不可靠**：思源系列 `familyName="Gen Shin Gothic P Medium"` 但 `subfamilyName` 恒为 `Regular`/`Bold`。判断字重必须从**文件名**提取。
2. **文件名优先于 subfamilyName**：否则 `思源黑体-Medium.otf`（sub=Regular）会被误判为 400 而非 500，导致档数统计少算。
3. **带字重后缀的 familyName 会被误拆字族**：如「梦源宋体-W3…W9」各自 familyName 不同，按 familyName 归组会把 10 档拆成 10 个"字族"。**应按文件所在目录归组**。
4. `data.json` 字段：`byte/size/ctime/postscriptName/fullName/familyName/subfamilyName/version/numGlyphs/copyright` 为自动生成；`type/license/home/baidu/officialDownload` 为人工维护（故缺失率高）。

### 对 CorgiMemo 的选型结论（直击"中文字重撞档"痛点）
内置多字重中文字体是解决 B1(500)/B2(700)/B3(900) 撞档的根本办法。本库多字重中文字体排行（按目录归组）：
- 梦源宋体/黑体 10 档 65535 字形（643–994 MB，过大）
- 小米 MiSans 8 档 29601 字形 76.9 MB
- 獅尾半月字體 7 档、初夏明朝體 7 档、源样明体 7 档、思源宋体 7 档
- **思源黑体 6 档 30888 字形 55.8 MB**（首选）
- 源音黑體 6 档 65535 字形 120.6 MB（满覆盖）
- **阿里巴巴普惠体 5 档 28987 字形 38.6 MB**（体积最优）

**首选思源黑体**：已核对实际文件 7 个（ExtraLight 7.4M / Light 8.0M / Normal 8.0M / Regular 8.0M / **Medium 8.1M** / **Bold 8.3M** / **Heavy 8.4M**）。其中 **Medium(500)/Bold(700)/Heavy(900) 精确对应 B1/B2/B3 三档**，只内置这 3 档约 **24.8 MB**。

落地路径：拷贝所需档位到 `app/src/main/res/font/`（**不要子模块**）→ 建 FontFamily → 改 `Type.kt` 的 `fontFamily = FontFamily.Default` → 同步字重可用集合常量 → 档位自动派生 500/700/900 三档分明；`FontWeightProbe` 保留作兜底置灰。
