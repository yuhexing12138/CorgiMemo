## 复选框标识跟随缩进（用户反馈修复）
- 反馈：点击「增加缩进 / 减少缩进」按钮时，复选框块里的**复选框标识不跟随文本一起缩进**（只有文字右移）。
- 根因：缩进由库在**文本层**实现——纯文本段走 `setParagraphIndent`（段落属性，编码端输出段首全角空格 U+2003×2/级）、列表段走 `setListMarker`（段落 textIndent 30sp/级）；而复选框标识是 `BlockTextItem` 的 Row 内独立 Composable、位于编辑器左侧，不参与文本排版 → 文本缩进它不动。
- 修复（编辑页 + 详情页两端同步）：
  - 新增共享 Composable `checkboxIndentDp(bodyMarkdown, fontSize)`（CheckboxIcon.kt）：按段落自身缩进层级换算等宽偏移——列表段用 `LIST_LEVEL_INDENT_SP`(30sp)/级，纯文本段用 `PLAIN_INDENT_STEP`(2) × 字号（EM 空格宽度 = 1em = 字号，字号 Unspecified 兜底 15sp）；一级返回 0dp。
  - 调用方把结果加到复选框的 `Modifier.padding(start = 2.dp + indentDp)`：编辑页 `BlockTextItem`（字号取 `LocalContentTypography.current.bodyLarge.fontSize`）、详情页 `InspirationBodyRichText`（固定 15.sp）。
  - **必须显式读 `state.annotatedString`** 注册快照依赖：`setParagraphIndent`/`setListMarker` 只写 annotatedString（段落 type 是普通 var，非快照），不读它则缩进后复选框不重组（与 `canIncreaseIndent`「到顶不置灰」同款坑）。
  - 可见性调整（同包复用）：`PLAIN_INDENT_STEP` → internal；`plainIndentLevelOfMd` → internal；新增顶层 internal `listLevelOfMd`（原 controller 私有成员删除，调用点统一解析到顶层，行为不变）。
- 边界确认：EM 空格 U+2003 不属于 Kotlin 正则默认 `\s` 集合，故「缩进 + 内容以 '- ' 开头」不会被误判为列表段（仍按纯文本层级算缩进）。
- 静态检查：3 个改动文件括号平衡通过、无重复定义；未编译（按约定）。

## 复选框跟随缩进：修正每级宽度来源（第二次修复）
- 用户反馈（承接上一条）：缩进时复选框虽跟随，但**与文本的间距会变化**（不同步）。
- 根因（查库源码确认）：`compose-rich-editor/.../paragraph/type/DefaultParagraph.kt` —— 纯文本段缩进是**段落样式** `TextIndent(firstLine = restLine = indent × (level-1))`，步长 `indent = config.orderedListIndent`（App 配 `LIST_LEVEL_INDENT_SP`=30sp）；列表段同公式。**段首那两个 EM 空格（U+2003）只是 markdown 持久化载体**（编码端 appendParagraphStartText 输出 / 解码端 PARAGRAPH 钩子剥除还原 level），**不是渲染出来的字符**，与字号无关。
- 首版错误：我把"持久化载体的 EM 个数 × 字号"当成渲染宽度估算 → 字号≠15sp 时与文本实际缩进（固定 30sp/级）不等，层级越深偏差越大 → 间距渐变。
- 修正：`checkboxIndentDp(bodyMarkdown, perLevelSp = LIST_LEVEL_INDENT_SP)` —— 每级宽度直接用库渲染步长（编辑页传块 `state.config.orderedListIndent` 严格对齐实际值；详情页用默认 30sp，与其 config 一致）；删掉 TextUnit/isSpecified import（不再依赖字号）。
- 结论：缩进量 = (层级-1) × 30sp，纯文本段与列表段同；据此复选框与文本同步位移、间距恒定。
- 静态检查：3 文件括号平衡通过、无残留 fontSize/TextUnit 引用；未编译（按约定）。

## 复选框跟随缩进：改测量级同步（第三次修复）
- 用户反馈（附两张真机截图）：缩进三次后复选框与文本间距明显增大。像素测量：文本位移 ≈ 复选框位移的 **2 倍**（复选框 ≈ 3×30sp 符合公式，文本 ≈ 180sp）。
- 排查（库源码）：`DefaultParagraph.getNewStyle` 理论公式 `TextIndent(firstLine=restLine=indent×(level-1))`、`indent = config.orderedListIndent`(30sp)；`updateParagraphType` 对 startText 为空的纯文本段只换 type 不写文本（编辑态无 EM 字符）；编码/解码钩子都只在 markdown 边界。**静态读码无法解释 2 倍**（TextIndent 在多段落 TextField 的实际应用行为存疑，未再深挖）。
- **结论与方案**：放弃"公式对齐"路线（两轮都被实际渲染打脸），改**测量级同步**——复选框偏移直接用 `onTextLayout` 回调里 `TextLayoutResult.getLineLeft(0)`（库渲染出的首行左缘 = 实际缩进量 px→dp）。对库的任何渲染行为都数学恒等，间距恒定。
- 实现（3 文件）：
  - `BodyBlocksEditor.kt`：`BlockTextItem` 加 `measuredCheckboxIndent`（remember(block.state)，初值=checkboxIndentDp 公式近似，`RichTextEditor.onTextLayout` 实测覆盖；回调内禁读 CompositionLocal → 组合期捕获 `density`）；删除原公式直连与 annotatedString 显式读。
  - `InspirationViewCard.kt`：`InspirationBodyParagraph` 加 `onTextLayout` 参数透传 `RichText`（库 material3.RichText 有该参数）；复选框段 `var indentDp by remember(bodyMd)` 同款"公式初值+实测覆盖"；import 补 mutableStateOf/getValue/setValue/LocalDensity/TextLayoutResult。
  - `CheckboxIcon.kt`：`checkboxIndentDp` KDoc 降级为"首帧初值公式"，注明权威值恒为实测。
- 用户问"复选框能否列表化"：评估过——作为库列表段落类型承载（marker 与文本同步由库保证）是最正统路径，但需库新增段落类型+载体重设计+marker 可点击命中+两端联动，工程量大；测量同步改动小且对任何渲染机制成立，先落此案，列表化留作演进选项。
- 教训沉淀：**对第三方库"估算渲染量"不可靠时，直接测量布局结果（onTextLayout/getLineLeft）是唯一稳定路径**。
- 静态检查：3 文件括号平衡 + 关键代码抽查全过；未编译（按约定）。

## 测量级同步失效根因：getLineLeft 恒 0（第四次修复）
- 用户反馈：编译通过，但复选框**完全不跟随**文字移动了。
- 根因：`TextLayoutResult.getLineLeft(0)` 返回**行盒子左缘**（LTR 下恒 0）——TextIndent 只移动**字形绘制起点**、不改变行盒子，用它测缩进恒得 0 → measuredCheckboxIndent 被实测值钉死在 0 → 复选框不再跟随（比公式版更糟）。
- 修复：改 `getHorizontalPosition(0, usePrimaryDirection = true)`——返回**首字符实际绘制 x**（字符级、包含缩进量），语义精确。两处（编辑页 onTextLayout / 详情页同）都换，并加空文本防御（layoutInput.text.text.isNotEmpty，防 getHorizontalPosition 对空文本越界异常）。
- 教训沉淀：**TextLayoutResult 测缩进用 getHorizontalPosition(0, true)，绝不用 getLineLeft/getLineTop（行盒子 ≠ 字形位置）**。
- 静态检查：括号平衡 ✓、getLineLeft(0).toDp() 残留 0 处；未编译（按约定）。

## 复选框缩进终极方案：App 布局级缩进（第五次修复，用户建议"列表化"落地）
- 用户反馈：getHorizontalPosition 实测方案依旧不同步（现象与图二完全一样）；要求探索列表化。
- **根因收敛**：三轮失败（公式 30sp/级、getLineLeft 恒 0、getHorizontalPosition 仍差一半）证明——**编辑器外（Row 内）组件想对齐库排版体系内的缩进量，无论估算还是测量都不可靠**。列表的 marker+文本之所以永远同步，是因为它们是**同一个排版整体**。
- **终极方案（布局级同步）**：复选框块的缩进**彻底不进库排版**——
  1. `BodyBlock.Text` / `BlockSpec.TextSpec` 加 `indentLevel: Int = 1`（App 自管档位，1..6）；
  2. markdown 载体 = `- [ ] `/`- [x] ` 之后、内容之前的 EM 前缀（每级 2 个 U+2003，**App 自编自解，不经库编码端**，state 恒干净无 TextIndent）；
  3. `checkboxMarkdownInfo` 改返回 Triple(checked, indentLevel, contentMd)（剥载体）；
  4. `toMarkdown` 拼 `checkboxMdPrefix + plainIndentPrefix(indentLevel) + body`；
  5. 渲染：Row 内复选框图标 padding(start = 2 + L×30sp) + 编辑器 padding(start = L×30sp)——**同一偏移推动两者，同步是布局恒等的**（数学上间距不可能变），与库渲染行为完全解耦；这正是列表项"marker+文本整体缩进"的行为模式，即用户要的"列表形式"；
  6. 缩进操作：`indentFocusedBlock` 复选框分支 → 新命令 `SetCheckboxIndentCommand` → `setCheckboxIndent` 就地换块对象（state/history/光标无损，与 setCheckboxChecked 同模式）；canIncrease/canDecreaseIndent 复选框分支读块对象 indentLevel；
  7. 传递：split/normalize/merge/插图拆块（并修了插图丢 checked 的旧遗漏）全部继承源块 checked+indentLevel；退出复选框（块首退格/空项回车）checked=null + indentLevel 归 1；
  8. 详情页：同公式双 padding（复选框 + 段落），点击勾选翻转前缀时**保留缩进载体**；
  9. 删除全部测量代码（measuredCheckboxIndent/onTextLayout/checkboxIndentDp/density 捕获）与旧 KDoc。
- **教训沉淀**：跨排版体系的对齐问题，优先改架构（把元素放进同一容器整体变换），而不是对齐外部体系的数值（公式/测量都是对抗性补丁）。"列表化"的正确实现 = 整体缩进行为，不必真改库段落类型。
- 静态检查：3 文件括号平衡 ✓、测量残留 0、载体关键点全就位、sp/LocalDensity import 补齐；未编译（按约定）。

## 复选框跟随对齐（用户确认缩进同步已修复后新需求）
- 缩进同步（双 padding 修复后）用户确认 ✓。新需求：左/中/右对齐时复选框也跟随。
- 机制分析：对齐走库 textAlign（Screen 里 toggleParagraphStyle），**textAlign 与 TextIndent 的行盒机制不同**——textAlign 由排版对齐处理、行盒随对齐整体移动（getLineLeft 反映真实偏移）；TextIndent 只移字形起点（getLineLeft 恒 0，缩进场景不可用已由布局级方案替代）。**对齐场景 getLineLeft 是标准测量，可信**。
- 实现（BlockTextItem）：`alignmentOffset`（remember(block.state)，初值 0dp）+ `RichTextEditor.onTextLayout` 实测 `getLineLeft(0).toDp()` 回写 + 复选框 `Modifier.offset(x = alignmentOffset)`（offset=绘制偏移不改布局，与缩进 padding 独立叠加）。**无需自管对齐状态**：toggle 取消对齐 → lineLeft 归 0 → 自动复位。offset 恒 ≥0（三种对齐的行左缘都不小于 0），不会撞拖拽手柄。
- 详情页无需改（textAlign 不持久化，详情页无对齐概念）。
- 风险注记：getLineLeft 对 textAlign 的可靠性未经真机验证（与已证伪的 TextIndent 测量机制不同，理论上应可靠）；若实测不跟随，需退回"非左对齐隐藏复选框"或 inline 方案（BasicTextField 1.11 无 inlineContent，成本高）。

## 普通块缩进不生效修复（渲染侧遗漏）
- 用户反馈：普通文本行按缩进按钮文本不动。
- 原因：布局级缩进统一到所有块时，**命令侧**（indentLevel ±1）统一了，但**渲染侧**只给复选框块挂了 padding——普通块的编辑器没挂，档位变了视觉不动。
- 修复：BlockTextItem 新增 `plainBlockIndentPadding`（checked==null && !isList 时 = (L-1)×30sp，否则 0）挂到编辑器 start padding；复选框块的编辑器恒 0（复选框 padding 已推，双加会复现间距 bug）。
- 最终几何：普通块 = 编辑器 padding P；复选框块 = 复选框 padding(16dp+P)（编辑器 0，被自然推动）——普通块文本左缘与复选框标识左缘同列 ✓。

## 列表换行右跳一帧修复（第十四轮，库改动）

- 修复：BlockTextItem 的 Row 加 `pointerInput(Unit) { awaitPointerEventScope { while(true) { awaitFirstDown(requireUnconsumed=false); controller.onTextBlockPressed() } } }`——只观察按下不消费事件，TextField 点击定位/长按选择/双击选词手势不受影响；controller 新增 `onTextBlockPressed()`（= clearBlockSelection）。
- 顺带清理：BlockTextItem 里历史上重复的两段复选框注释合并为一段（第一段在编辑中被截断后删除残片）。
- 模式沉淀：**"点击已聚焦的组件"不产生任何焦点/selection 之外的信号**——需要感知它只能用非消费的 awaitFirstDown 观测 down 事件（awaitFirstDown 默认 requireUnconsumed=true 会漏掉被消费的 down，必须显式传 false）。
