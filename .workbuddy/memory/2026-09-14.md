## 上游核查：compose-rich-editor 原作者是否新增「跨块连续选中」
- 本机 git 走代理访问 github.com 返回 502（剥离代理变量后仍受 shell 环境破坏影响：cat/head/sed/cd 缺失）。改用 WebFetch 直连原作者仓库（走独立通道，正常）。
- 核查对象：上游 `MohamedRejeb/compose-rich-editor` 的 `richeditor-compose/.../model/RichTextState.kt` 与仓库页。
- 结论：**原作者库从未、且架构上无法提供「跨多个独立编辑器实例（Block）连续选中文本」能力**。
  - `RichTextState.selection` 类型为单实例 `TextRange`，setter 强校验 `value.max <= textFieldValue.text.length`，范围无法指向其他实例文本；各 `RichTextState` 经 `rememberRichTextState()` 完全隔离，无共享引用、无 cross-block/multi-editor 选区概念；无 `selectAll`/`onSelectionChange` 等公共跨块 API。
  - 最新上游动态（2026-09-05）为 bump coil 等依赖；近期特性为 undo/redo history、`compose-1.12`、json 模块、文档，均无跨块选择。
- 区分：库**支持单编辑器内跨多段落选中**（一个 AnnotatedString），但**不支持跨多个独立编辑器块**——后者即 App 层此前自实现的 feature，库无等价原生实现可"恢复"。删除该 feature 逻辑自洽、无上游替代。

## 上游核查：compose-notion-editor 类库是否满足「跨 Block 连续选中」
- 无字面名为 `compose-notion-editor` 的仓库；Compose 原生 Notion 风格块编辑器最知名的是 `linreal/cascade-editor`（io.github.linreal:cascade-editor，"Notion/Craft editing model, natively in Kotlin"，活跃）。用户的项目依赖中未引用任何 notion 编辑器。
- 核查 `cascade-editor` 源码 `editor/.../state/BlockTextStates.kt`：
  - `private val states = mutableStateMapOf<BlockId, TextFieldState>()` —— **每块一个独立 TextFieldState**（与旧 App 实现、compose-rich-editor 同架构）。
  - `getSelection(blockId)` / `setSelection(blockId, TextRange)` 均为**单 block 维度**，无任何接受多 block 或跨块 range 的方法。
  - README 亦明确"each text-capable block owns a long-lived TextFieldState"，且**未提及**任何跨块文本选择、选择手柄、长按拖拽跨块选择。
- 结论：**cascade-editor 不满足**该需求。其架构（每块独立文本字段）与已删除的 App 实现、compose-rich-editor 完全一致——跨块连续选中本质上必须由 App 层自实现，库层无法提供。若改用此类块编辑器，该 feature 仍需自行 glue（即此前被删除的那套逻辑）。
- 注：Notion 网页版支持跨块选择，但 Compose 重实现普遍因"每块独立 TextField"而缺失。如用户指其他具体库（如 vivekgjoy/NotionComposeEditor）可再查，结论大概率相同。

## 研究：跨块文字选择的"库 / 实现方法"替代方案
- 用户要求查找"有长按手柄 + 滑动跨多个 Block 连续选中"能力的 GitHub 库，或其他更好实现方法。
- **库的诚实结论**：所有被点名/候选的可编辑块编辑器都不支持可编辑跨块连续选中：
  - `compose-rich-editor`（原作者及本机 fork）：单实例 `TextRange` selection，无跨块。
  - `linreal/cascade-editor`：每块独立 `TextFieldState`，无跨块。
  - `MickeyLaw/ComposeMarkdownBlockEditor`、`nguyenvukhang/compose-notion-editor`：仓库不存在。
  - → 根因：Compose 块编辑器普遍"每块独立 TextField"，跨块连续选中原生平不支持。
- **新发现 A —— Compose 1.12 `SelectionState` + `SelectionContainer`（只读/选区态原生方案）**：
  - 1.12（2026-08 版）新增 `rememberSelectionState()`，传入 `SelectionContainer(state=)`，支持 `selectAll()/clear()/select(TextRange 全局范围)/extendSelectionByWord()`；`select(TextRange)` 与 `extendSelectionByWord()` **可跨越容器内多个 `Text` 组合项**（全局 range），并支持拖动选区越 viewport 自动滚动。
  - 这是"阅读/选中态"跨多个 Block 选中的现成方案（含手柄、全选、按词跨块扩展），但 **`SelectionContainer` 仅用于可选中文本，不是可编辑 TextField**——即不能边编辑边跨块选，需编辑态/选择态分离。
- **新发现 B —— `konecny-ondrej/compose-markdown-editor`（可参考架构）**：
  - WYSIWYG Markdown 编辑器（Compose Multiplatform，MIT，仅 ~7 stars / v0.3.0 / 以 jvmMain 为主，不成熟）。
  - `InteractiveContainer` 集中管理"视觉选择（用户看到被选中的文本）"并含全部文档组件；`InteractiveText` 为可编辑文本。selection 集中管理是其架构亮点，可作为自建跨块选择层的参考，但不建议直接依赖。
- **项目现状**：`gradle/libs.versions.toml` 中 `compose = "1.9.2"`、BOM `2026.04.01`、Kotlin `2.4.0`。要用 1.12 的 `SelectionState` 跨块选中，需先把 Compose 升到 1.12（注意 compose-rich-editor fork 是否兼容 1.12 的富文本编辑模型变更）。
- **实现路线（按性价比）**：
  - 路线 A（推荐，若需求=选中复制/分享）：升级到 Compose 1.12，在"浏览/选中态"把各 Block 渲染为 `Text` 并统一包进一个 `SelectionContainer(state=selectionState)`，原生获得跨块手柄选词/全选；编辑态仍用现有每块 TextField。代价最低。
  - 路线 B（可编辑且跨块）：整个文档作为一段 `AnnotatedString` 放进单个 `BasicTextField`，Block 用 ParagraphStyle/InlineTextContent 区分。selection 天然跨块；但图片/勾选/附件等非文本块极难塞入，与现有 per-block 架构改动巨大。
  - 路线 C（最灵活最重，即此前被删方案）：全局手势观察 + 自建手柄 + 跨块高亮；若重做建议收窄到相邻可输入块。
  - 路线 D：参考 `compose-markdown-editor` 的 InteractiveContainer 集中 selection 架构。
