### 撤销/重做的正确判定 API（重要）

BlockNote **公开** `editor.can(editor.undo)` / `editor.can(editor.redo)` 返回 boolean。
原理（读 `node_modules/@blocknote/core/src/editor/managers/StateManager.ts`）：
`can(cb)` 置 `isInCan=true` 调 cb，`exec()` 见 `isInCan` 走 `canExec()` 分支——**只判定不 dispatch**，
绝不污染历史栈。
> ⚠️ 不要走 `editor._tiptapEditor.can().undo()`（私有字段、跨版本易碎），也别
> `editor.on("transaction", ...)`——`BlockNoteEditor extends EventEmitter<{ create: void }>`，
> **只有 `create` 一个事件**，没有 transaction 事件（`EventEmitter.ts` 的 `emit` 是同步的）。

`editor.on("update", cb)` 存在但不覆盖全部路径，故本方案用「onChange + undo/redo 后主动推」覆盖。

### 1. 把产物重建接进 Gradle（`app/build.gradle.kts`）

新增 `buildBlockNoteEditor`（`Exec` task，group=blocknote）：

| 要素 | 做法 | 为什么 |
|---|---|---|
| 可执行文件 | `npm.cmd`（Windows）/ `npm` | Windows 上 npm 是批处理，直接调 `npm` 找不到可执行文件 |
| 增量 | `inputs.dir(src)` + `inputs.file(editor.html/vite.editor.config.ts/package.json/package-lock.json)` + `outputs.file(editor.html)` | 源码未动时 UP-TO-DATE，不必每次吃 45 秒 vite |
| 失败降级 | `isIgnoreExitValue = true` + 失败时落**标记文件** | 未装 node 的机器仍能编 App；但吞掉失败会让 Gradle 缓存「成功」态 → 下次跳过 → 永远拿旧产物。故落 `build/blocknote-editor-build.failed`，配合 `outputs.upToDateWhen { !marker.exists() }` 强制下次重试。**绝不删已有 editor.html**（删了运行时白屏，比旧产物更糟） |
| 挂依赖 | `tasks.configureEach { if (name.startsWith("merge") && name.endsWith("Assets")) dependsOn(...) }` | ⚠️ 不能用 `tasks.matching{}.configureEach{}`——matching 在调用时刻绑定集合快照，而 AGP 的 merge*Assets 由 variant API 晚注册，会**静默失配**。configureEach 对「此后注册的每个 task」都回调，天然免疫时序 |

> ⚠️ **`executionResult` 不能在 `upToDateWhen` 里读**：up-to-date 检查发生在 task 执行**之前**，
> 那时 `Provider<ExecResult>` 尚无值，读会抛异常。这就是必须用标记文件的原因。
> （`Exec` 的 API 已用 javap 核实：`AbstractExecTask.getExecutionResult(): Provider<ExecResult>`、
> `isIgnoreExitValue()/setIgnoreExitValue(boolean)`；`org.gradle.api.logging.Logger extends org.slf4j.Logger` 故 `warn` 可用）

## 修复：撤销/重做按钮恒灰（v1.10，`editor.can` 根本不存在）

**用户提问（两次）**：「为什么灵感编辑页左上角的撤销和恢复按钮一直是灰的？」
→ 我第一次给的修复**也是错的**，用户反馈「还是灰的」，第二轮才挖到真根因。
**不是编译问题、不是产物滞后**——是纯 JS 逻辑 bug + 错误 API。

### 真根因（一句话）

**`BlockNoteEditor` 原型上根本没有 `can` 方法**，只有 `exec` / `canExec`。
原代码（v1.7 起）写的 `editor.can(editor.undo)` → 运行时 `TypeError: ed.can is not a function`
→ 被 `catch { return; }` 静默吞掉 → `undoState` 永不上行 → 按钮恒灰。

已精确核实（`node_modules/@blocknote/core/src/editor/BlockNoteEditor.ts`）：
```bash
# 全类搜 `public can` / `can:` / `can =` / `.can` —— 零匹配
```
只有：
```ts
public exec(command: Command) { return this._stateManager.exec(command); }
/** @example if (editor.canExec(command)) { show button } */
public canExec(command: Command): boolean { return this._stateManager.canExec(command); }
```
`StateManager.can(cb)` **从未被转发到 editor 上**（它自己那个 `@example` 注释写
`editor.can(editor.undo)`——**是误导性文档，与实际不符**）。

### 两轮都踩同一坑的原因（踩坑记录）

| 写法 | 结果 |
|---|---|
| `ed.can(ed.undo)`（v1.7 原始） | `ed.can is not a function` → TypeError |
| `ed.can(undoCommand)`（我第一轮"修复"） | **同样** `ed.can is not a function` → TypeError |
| `ed.canExec(undoCommand)` ✅ | 正确 |

**第一轮的误判**：我只顾着论证「`can(cb)` 内部是无参 `cb()`，所以传实例方法会丢 this」，
却**没有验证 `editor.can` 这个方法是否存在**。凭「BlockNote 有 `can`」的先验往下推，
结果是在一个不存在的方法上做精细论证。

> 补记：即便 `can` 存在也传不得裸引用——`can(cb)` 内部是无参 `cb()`：
> - 传实例方法 `ed.undo` → `this` 丢失 → `this._stateManager` 抛 TypeError；
> - 传 prosemirror 命令 → state 为 `undefined` → `buildCommand` 内
>   `historyKey.getState(undefined)` 抛 TypeError。
> 但这些都是**次要的**，主因是方法不存在。

### 正确形态

`canExec(command)` → `_stateManager.canExec(command)` → `command(state, undefined, view)`
——用**真实** prosemirrorState 调命令（`dispatch === undefined` ⇒ 只判定不派发）。
`StateManager.undo()` 内部即 `this.exec(undoPlugin.undoCommand)`，命令来源一致：

```ts
const undoPlugin = this.editor.getExtension<typeof HistoryExtension>("yUndo");
if (undoPlugin) { return this.exec(undoPlugin.undoCommand); }
const historyPlugin = this.editor.getExtension<typeof HistoryExtension>("history");
if (historyPlugin) { return this.exec(historyPlugin.undoCommand); }
throw new Error("No undo plugin found");
```
`History.ts` 里 `undoCommand: undo, redoCommand: redo`（`@tiptap/pm/history` 的
`undo` / `redo`，`Command = (state, dispatch?, view?) => boolean`）。
`prosemirror-history` 的 `buildCommand` 实测：
```js
return (state, dispatch) => {
    let hist = historyKey.getState(state);
    if (!hist || (redo ? hist.undone : hist.done).eventCount == 0) return false;
    if (dispatch) { ... }
    return true;
};
```
—— 正因它第一行就解 state，传 undefined 必崩；而 `canExec` 恰好补上 state。

**关键事实**：`HistoryExtension` 由 `getDefaultExtensions()` 无条件注册（`extensions.ts:171`），
`"history"` / `"yUndo"` 两个 key 必有一个存在，无需额外配置。

### 改动

| 文件 | 改动 |
|---|---|
| `blocknote-probe/src/editor/EditorApp.tsx` | 新增 `getHistoryCommands()`（`getExtension("yUndo") ?? getExtension("history")` 取 `undoCommand`/`redoCommand`，KDoc 记录完整陷阱链）；`pushUndoState` 改用 **`ed.canExec(...)`**；`catch` 改为 `sendUp({type:"error", ...})` 上报而非静默 return；`useEffect` 依赖数组补 `getHistoryCommands` |
| `docs/bridge-protocol.md` | 修正 `undoState` 判定说明（原文写的 `editor.can(editor.undo)` 是错的），补 ⚠️ 陷阱段落 + `transact()` 限制；版本记录 v1.10 |

### 教训（两条，都比上一条更值钱）
1. **`catch { return; }` 是隐形杀手**：任何「静默失败 + 上层无从感知」的 catch 都应至少上行一次诊断。
   这次按钮恒灰排查两轮，就是被它掩盖的——第一轮若已有 error 上报，logcat 里
   `ed.can is not a function` 会直接指出问题。
2. **⚠️ 不要在未验证「方法是否存在」的前提下论证它的语义**。第一轮的失误不是推理错，
   而是**跳过了存在性验证**：花力气推 `can(cb)` 的参数语义，却没跑一句
   `grep 'public can' BlockNoteEditor.ts`。**遇到「API 看起来应该有但没反应」，

## 优化建议落实（v1.9.1）：背景色单一真值 + 无限高约束穿透修复

### ① 背景色收敛为「内容区唯一真值」✅

## 编译错误修复：`remember` lambda 内读 `MaterialTheme`（v1.9.2）

**报错**：`InspirationEditScreen.kt:537:27 @Composable invocations can only happen from the context of a @Composable function`

**根因**：`contentBackgroundColor` 的 `remember` 写法把 `MaterialTheme.colorScheme.background`
放进了 calculation lambda **内部**：

```kotlin
// ❌ calculation lambda 是普通 lambda（非 @Composable），在组合之外执行
val contentBackgroundColor = remember(userPickedBackgroundColor, MaterialTheme.colorScheme.background) {
    if (userPickedBackgroundColor == Color.Transparent) {
        MaterialTheme.colorScheme.background   // ← 537 行报错
    } else userPickedBackgroundColor
}
```

**迷惑点**：同一表达式里，**key 参数的 `MaterialTheme.colorScheme.background` 完全合法**——
`remember` 的 key 在组合期求值；只有**大括号内**（缓存计算，组合之外）非法。
「一半合法一半非法」是这个错误容易被忽略的原因。

**修复**：把组合读取提到 `remember` 外部存成普通局部变量：

```kotlin
val themeBackgroundColor = MaterialTheme.colorScheme.background   // 组合期 ✅
val contentBackgroundColor = remember(userPickedBackgroundColor, themeBackgroundColor) {
    if (userPickedBackgroundColor == Color.Transparent) themeBackgroundColor
    else userPickedBackgroundColor
}
```

**顺带全文件排查**：其余 8 处 `remember`（611/612/908/1543/1726/1731/1796 行）lambda 内均为纯计算
（`mutableStateOf` / 字符串格式化 / `dp` 乘法），无同类问题。`themeBackgroundColor` 命名唯一无冲突。

**已沉淀到 MEMORY.md 新增「⚠️ Compose 高频陷阱」节**，含同类场景（`derivedStateOf`）与
「key 合法 / lambda 体非法」的判别要点。

⚠️ **未编译**（遵守约定），需用户重新构建验证。
