# 段内换行与选区手柄跳变 · 深改方案

> 范围：灵感编辑页正文块（`BodyBlocksEditor` + richeditor 库）
> 问题来源：用户实测——块内多行时，从第 1 行行首拖动选择手柄到行尾，光标**立马跳到第 2 行行首**
> 产出日期：2026-09-15
> 状态：**方案待评审（未动代码）**；简单改法已试并回退，结论见 §3

---

## 一、需求（用户确认的行为口径）

| 行为 | 期望 |
|------|------|
| 拖拽过程 | 光标**始终跟手**移动 |
| 到达行尾后继续向右拖 | **保持在行尾**（不跳到下一行） |
| 到达行尾后向下拖 | 跟手移动到**下一行的对应位置** |
| 反向（从下行往上行拖） | 同理，不应有跳变 |

---

## 二、现状与根因（精确机理）

### 2.1 库的段落承载方式

库里**段落不是由 `\n` 承载的**，而是由 `ParagraphStyle` 的 range 边界承载。为此做了两个 hack
（均在 `RichTextState.updateAnnotatedString` / `updateRichParagraphList`）：

```kotlin
// ① 文本层把 \n 全部替换成空格（段落边界由 ParagraphStyle 负责换行）
val newText = if (singleParagraphMode) newTextFieldValue.text
              else newTextFieldValue.text.replace('\n', ' ')
// ② 每个段落末尾追加一个"有宽度的占位空格"
//    （原注释：修 Compose「多段落时最后一个字符不可选」）
if (i != richParagraphList.lastIndex && index < newText.length) { append(' '); index++ }
```

### 2.2 跳变的成因

设一个块内有两行「第一行 / 第二行」，则：

```
用户看到：   第一行          ← 换行（ParagraphStyle 边界）→
annotatedString： 第一行 · 第二行            （· = 段末占位空格）
offset：      0 1 2  3  4 5 6
                     ↑        ↑
              第1行"行尾"   第2行行首
              offset = 3    offset = 4
```

- 第 1 行的**行尾位置没有属于自己的 offset** —— offset 3 是占位空格，offset 4 已是第 2 行的首字符；
- 选择手柄拖到行尾继续往右时，`getOffsetForPosition` 把"超出行宽"的位置算作**该行最后一个位置之后**，
  即 clamp 到 offset 4 → 视觉上就是**跳到第 2 行行首**；
- 占位空格越宽/越"隐藏"，这个跳变越像"突然跳走"。

**一句话**：**「行尾」在文本坐标里没有落脚点**，这才是根因 —— 不是 Compose 的问题，是段落承载方式的副作用。

## 三、已排除的方案（实测结论，勿重试）

**「把段落分隔换成真实 `\n`」**（去掉 ① 的替换 + ②的占位空格改 `append('\n')`，共 4 处）——
2026-09-15 试过并**已回退**，因为它与库架构根本冲突：

| 坑 | 说明 |
|----|------|
| **双重换行** | `ParagraphStyle` 的 range 边界**本身就会另起一行**（`MultiParagraph` 逐段垂直堆叠）。段末再写一个 `\n`，会在段落之间**多出一个空行** |
| **段落数爆炸** | `checkForParagraphs()` 会扫描文本里**所有** `\n` 并拆成新段落；它原本依赖"文本层没有 `\n`"来区分「用户新输入的换行」与「段落分隔」。一旦段落分隔也变成 `\n`，每次文本变更都会把已有段落**再拆一次** |

> 这两条已写进库代码的**警示注释**（子模块 `03ae90e` / 主仓库 `b0334529`），避免后人重蹈。

## 四、候选方案

### 方案 A（推荐先验证）：块内换行改用 LINE SEPARATOR（U+2028）

**思路**：块内换行不再用 `\n`，而用 Unicode 的 `U+2028 LINE SEPARATOR`。

为什么它能绕开所有上述坑：

| 关注点 | 表现 |
|--------|------|
| 库是否会把 `\u2028` 拆成新段落 | **不会**。`checkForParagraphs` 只找 `\n`；`replace('\n',' ')` 也不影响它 → 段落数不变 |
| 视觉换行 | `\u2028` 是标准行分隔符，Compose 文本排版按换行处理（**需真机确认**，见 §5 验证项 1） |
| 「行尾」有没有 offset | **有**。`\u2028` 是真实字符、占一个 offset → 手柄拖到行尾会 clamp 在它上面，**不会跳到下一行** |
| markdown 往返 | `toMarkdown()` 时把 `\u2028` 转回 `\n`；`initialize` / `createTextBlock` 时把 `\n` 转成 `\u2028`（**App 侧单点转换**，库不受影响） |
| 现有逻辑 | `effectiveText`、字数统计等按需把 `\u2028` 视作换行处理 |
| 与任务列表 / 列表共存 | 库的 `TaskList` / `UnorderedList` 段落仍是各自段落（回车在该段落内插入 `\u2028`，不新起段落）——**需真机确认**「列表项内换行」的 marker 表现 |

**改动面**（预计都不大）：
1. App 硬键盘 Enter / 软键盘 observer：插入 `\u2028` 而不是 `\n`（含"空缩进行回车"分支保持原样）；
2. App 粘贴多行：把粘贴内容里的 `\n` 转成 `\u2028`；
3. App `toMarkdown` / `initialize` / `createTextBlock`：`\u2028` ↔ `\n` 单点转换；
4. `effectiveText`、字数统计、`plainText`：把 `\u2028` 当换行；
5. 阅读卡：`InspirationViewCard` 的段内渲染同样需要认识 `\u2028`（它按 `\n\n` 拆段、段内交库渲染）。

**主要风险**：`\u2028` 在 Compose 里的换行与光标行为、以及中文 IME 组合态下的表现 —— 都是**真机一次性可验证**的（见 §5）。

### 方案 B：重做库的段落承载方式

让 `\n` 成为换行的唯一承载者，`ParagraphStyle` 退化为"纯样式"：

1. 文本层保留 `\n`，去掉占位空格；
2. **关键**：让"段边界不再额外换行"——但 `MultiParagraph` 逐段堆叠是 Compose 的固有行为，**无法关掉**；
   因此实际做法只能是**「整块合并为一个 ParagraphStyle range」**；
3. 代价：`TextIndent`（列表缩进、任务列表勾选框预留宽、有序列表 marker 悬挂）等**段落级样式全部失效** ——
   库的一半能力建立在这上面（列表 marker、任务列表勾选框、缩进层级都依赖 `ParagraphStyle`）。

**评估**：等于重写库的段落模型，且会丢掉核心能力（需要另行设计逐行样式方案）。
**成本 / 收益比明显不划算**，除非将来还要做"每行不同缩进"这类需求。

### 方案 C：接受现状

把跳变记为已知问题（成因已在库注释中写清），不做改动。
**代价**：拖拽手柄跨行时体验不佳；点击定位不受影响。

## 五、建议的推进方式与验证清单

**建议先做方案 A 的"最小可行性实验"**（改动 1 处：硬键盘 Enter 插 `\u2028`），
用真机确认下面 4 条后再铺开——如果第 1 条不成立，方案 A 直接作废，避免白做：

1. [ ] **换行是否正常显示**（`\u2028` 被 Compose 当换行，且不产生额外空行）
2. [ ] **拖拽手柄**：拖到行尾停住、继续右拖不变、下拖跟手到下一行对应位置（**本问题的验收点**）

4. [ ] **中文 IME**：跨行位置的拼音输入、候选词上屏是否正常

实验通过后，再按 §4 方案 A 的改动面铺开，并补跑：
5. [ ] 列表 / 任务列表内换行（marker 与勾选框的续行表现）

7. [ ] 阅读卡渲染（`\u2028` 在两端的显示一致）
8. [ ] 字数统计 / 复制全文（`\u2028` 按换行处理，不进字数）
