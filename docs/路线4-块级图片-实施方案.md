## 0. 最重要的一个发现：旧代码不能直接用

我原本判断"恢复成本比从零低"，依据是 `ReorderableColumn` 骨架还在。挖出历史版本后需要修正：

`git show 2dbd5855^:.../InspirationEditScreen.kt` 的结构是：

```
ReorderableColumn(图片/语音块)     ← 非文字块整体排在上方
        ↓
RichTextEditor（全部文字）          ← 文字是一个整体
```

也就是说，**内联化之前的实现也不是"图文交错"，而是"附件区 + 正文"**——图片只能成组出现在编辑器上方，不能插在段落之间。

所以：

- `ReorderableColumn` 骨架、拖拽排序、可见性追踪 → **可复用**
- `InlineImagePreview.kt` / `VoicePlayerComponent.kt` → **组件文件都还在**，未删除，可直接复用
- **块与文字的交错结构 → 必须新做**，这不是 revert，是新功能

## 1. 目标架构

### 1.1 数据结构：真正有序的混合块列表

```kotlin
// 现有（app/src/main/java/com/corgimemo/app/ui/model/ContentBlock.kt）
sealed class ContentBlock {
    data class Text(val content: String) : ContentBlock()
    data class Image(val path: String) : ContentBlock()
    data class Voice(val path: String, val duration: Int?) : ContentBlock()
}

// 改造后：加稳定 id；Image 预留后续需求字段
sealed class ContentBlock {
    abstract val id: String                      // 稳定标识：state 映射 + 重组 key
    data class Text(override val id: String, val content: String) : ContentBlock()
    data class Image(
        override val id: String,
        val path: String,
        // —— 后续需求预留（本期先不加列，见 4.3）——
        // val originalPath: String? = null,     // 裁剪不覆盖原图
        // val cropRect: String? = null,         // "l,t,r,b"
        // val displayWidthRatio: Float = 1f,    // 缩放
        // val note: String? = null,             // 备注
    ) : ContentBlock()
    // Voice 保留在数据模型中（旧数据/待办页仍在用），但灵感正文不再产生新的 Voice 块
    data class Voice(override val id: String, val path: String, val duration: Int?) : ContentBlock()
}
```

一个笔记正文就是一个有序列表：

```
[Text("今天去了西湖…"), Image(a.jpg), Text("沿着白堤走了一段…"), Image(b.jpg), Text("傍晚在楼外楼…")]
```

**语音在哪**：在 `Text` 块内部，仍以 `trigger:voice` token 内联（`Text.content` 是一段 Markdown，里面含语音 token）。**语音相关代码一行不改。**

### 1.2 渲染

```kotlin
ReorderableColumn(
    list = contentBlocks,
    onSettle = { from, to -> /* 拖拽排序 + 推撤销栈 */ },
    modifier = Modifier.fillMaxWidth(),
) { index, block, isDragging ->
    when (block) {
        is ContentBlock.Text  -> BlockTextEditor(block, ...)   // ← 每个 Text 块一个 RichTextEditor
        is ContentBlock.Image -> BlockImageCard(block, ...)    // ← 块级图片（裁剪/缩放/备注的落点）
        is ContentBlock.Voice -> BlockVoiceCard(block, ...)    // ← 兜底：仅旧数据迁移时可能出现
    }
}
```

`ReorderableColumn` 是泛型 `ReorderableColumn<T>`（底层 `sh.calvin.reorderable.ReorderableColumn`，`ReorderableList.kt:376`），content 是 `(index, item, isDragging)`，**天然支持异构列表**——Text / Image 混排没问题。

### 1.3 为什么必须是"多编辑器"

要图文交错，图片必须能插在**任意两个段落之间**。而 Compose 的 `BasicTextField` 不支持 `inlineContent`，图片无法进入文本排版。唯一办法是：

> 把正文拆成 N 个块，每个块一个独立编辑器，图片块作为普通 Composable 插在它们之间。

代价：`InspirationEditViewModel` 现在只持有**一个** `_richTextState`（`InspirationEditViewModel.kt:431`），要改成管理**N 个**。这是本次改造最大的单点改动。

## 2. 交互设计（最易翻车的部分）

| 场景 | 行为 |
| --- | --- |
| 块内按 Enter | 插入 `\n`（块内多段落），**不拆块** |
| 插入图片 | 在光标处把当前 Text 块**切成两块**，中间插入 Image 块；焦点移到后段块首 |
| Backspace 在块首（offset 0） | 前一块是 Text → 合并；前一块是 Image → 选中该图片块（两步删除，沿用现有交互） |
| Delete 在块尾 | 后一块是 Text → 合并到当前；后一块是 Image → 选中 |
| 方向键 / Home-End | 在块首↑、块尾↓ 时跨块跳转 |
| 删除图片块 | 移出列表；前后 Text 块**保持分离**（不自动合并，避免意外拼接） |
| 拖拽排序 | 图片块通过拖拽手柄触发；Text 块不参与长按拖拽（避免与文本长按选择冲突） |

**焦点管理**是本次最难的点：需要为每个块持有 `FocusRequester`，切块后把焦点移到后段块首。建议单独抽一个 `BlockFocusManager` 集中处理，不要把焦点逻辑散落在 UI 树里。

## 3. 落库改造

### 3.1 删掉正则反解析（顺带修掉历史 bug 源头）

现状：`saveInlineMediaBlocks(inspirationId, markdown)`（`InspirationEditViewModel.kt:1400`）用**正则从 Markdown 反解析**出 Image / Voice：

```kotlin
Regex("""!\[[^\]]*\]\(([^)]+)\)""")          // 块级图片
Regex("""\]\(trigger:image:([^)]+)\)""")     // 旧 trigger:image
Regex("""\]\(trigger:voice:([^)]+)\)""")     // 语音
```

这是字符串往返，脆弱，是历史上多个 bug 的源头。改为**直接遍历 contentBlocks 列表落库**，正则反解析整个删掉。语音因为仍内联在 Text 块里，仍需从 Text 内容中提取——但这部分逻辑可以从 `saveInlineMediaBlocks` 中**单独保留**，只服务于语音，缩小影响面。

### 3.2 需要 Room 迁移

`ContentBlockEntity`（`data/local/db/ContentBlockEntity.kt`）现有字段：`id / todoId / ownerType / type / filePath / duration / orderIndex / lineIndex`。

本期**至少**要新增：`blockId: String`（稳定标识）。后续需求再加 `cropRect / displayWidthRatio / note / originalPath`。

> 建议：**本期一次性把后续字段都加上**（nullable + 默认值），避免连续多次 migration。

### 3.3 文件删除要小心

`removeImagePath()`（`InspirationEditViewModel.kt:1281`）会**物理删除文件**（`ImageUtils.deleteImageFromInternalStorage`）。块级图片若复用此逻辑，会出现"删除块 → 撤销 → 文件已没了"的不可恢复情况。

建议：删除块只移出列表，物理文件走**延迟清理**（保存时统一回收）或回收站目录。

## 4. 为"句子中间插图"预留接口

你要求保留这个扩展位。做法是把**文本块的序列化**和**渲染**都抽象掉，将来换实现时不碰数据层：

### 4.1 序列化协议（数据层）

```kotlin
/** 文本块内容的序列化协议：本期 Markdown，将来可换 ProseMirror JSON */
interface TextBlockSerializer {
    val formatVersion: Int
    fun encode(state: RichTextState): String
    fun decode(raw: String, state: RichTextState)
}

object MarkdownTextBlockSerializer : TextBlockSerializer { override val formatVersion = 1 ... }
// 将来：class ProseMirrorTextBlockSerializer : TextBlockSerializer { override val formatVersion = 2 ... }
```

落库时把 `formatVersion` 一并写入（`ContentBlockEntity` 加一列，或复用 `Inspiration.contentFormat`）。将来升级时按版本分派解码器，旧数据无需批量迁移。

### 4.2 渲染策略（UI 层）

```kotlin
/** 文本块渲染策略 */
interface TextBlockRenderer {
    @Composable fun Render(block: ContentBlock.Text, /* … */)
}

/** 本期：每个 Text 块一个原生 RichTextEditor */
class ComposeBlockTextRenderer : TextBlockRenderer { ... }

/** 将来：一个 WebView（TipTap）承载全部 Text 块，支持行内图片 */
class WebViewBlockTextRenderer : TextBlockRenderer { ... }
```

### 4.3 为什么将来能平移

届时 `src / cropRect / note` 这些属性已经是 `ContentBlock.Image` 的字段，搬到 ProseMirror 节点 attrs 上是**平移**，不会白做。这也是我上次建议"先做路线 4"的原因。

**边界提醒**：预留接口不等于现在就实现抽象层的所有间接调用。建议本期只把 `TextBlockSerializer` 真正抽出来（成本极低、收益明确），`TextBlockRenderer` 只保留一个空接口 + 注释说明，避免过度设计。

| # | 风险 | 等级 | 缓解 |

| R1 | **多编辑器性能**：N 个 RichTextEditor 在 Column 里，长文档卡顿 | 中 | 本期先用 Column，实测；真出问题再考虑 LazyColumn + 状态外置（有状态编辑器做 Lazy 复用是坑，不要提前优化） |

## 7. 与后续三期需求的关系（这也是路线 4 最大的优势）

图片块是一个普通 Composable（`BlockImageCard`），所以三项后续需求**全部原生、零桥接**：

| 需求 | 路线 4 怎么做 |
| --- | --- |
| 缩放 | 宽度就是一个 state，拖拽把手直接画在 Composable 上，**不需要任何坐标换算**（对比路线 2 要 JS 上报 `getBoundingClientRect()` + 换算） |
| 裁剪 | 点击 → 原生裁剪 Activity → 回传新文件 → 更新块 `path` |
| 备注 | `BlockImageCard` 内嵌一个 TextField，`note` 存在块上，IME 完全原生可控 |

对比路线 2：这三项在路线 2 下分别需要 rect 上报、属性桥接、figcaption 语义冲突处理。这也是选路线 4 的决定性理由。

## 8. 待你确认的三个问题

1. **块内 Enter 是否真的不拆块？** 我建议不拆（复杂度低得多，用户感知不到差别）。但如果你希望"每个段落都是一个可独立拖拽的块"，那 Enter 就要拆块，工作量 +2~3 天。
2. **Room migration 是否本期一次性把后续字段（cropRect / note / displayWidthRatio / originalPath）都加好？** 建议加，避免连续迁移。
3. **旧数据迁移策略**：是"打开编辑页时懒迁移"（现状做法，保留 markdown 备份），还是"一次性全量迁移"？我倾向前者，风险可控。
