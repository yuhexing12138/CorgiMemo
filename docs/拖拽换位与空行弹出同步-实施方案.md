# 拖拽换位与空行弹出同步 —— 实施方案（方案 A1：提前提交 + 自接续滑行）

> 日期：2026-09-10
> 范围：灵感编辑页 `BodyBlocksEditor`（`app/src/main/java/com/corgimemo/app/ui/screens/inspiration/components/BodyBlocksEditor.kt`）
> 状态：**已按 A1 实施**（2026-09-10，未编译；实施记录见文末）

---

## 一、现象

灵感编辑页中相邻两张图片之间必须有空 Text 块（否则无法在两图间打字）。当把图片 A 拖到图片 B 旁边时：

1. 手指抬起 → 图片先"滑到位"（观感上换位已完成）；
2. 停顿约 **0.3~0.5s**；
3. 两图之间才"弹"出一个空行，下方内容整体下移一行。

用户诉求：**换位与空行弹出必须同步**。

## 二、根因

### 2.1 我们自己的代码是同帧的，问题不在我们这里

`BlocksReorderableColumn`（`BodyBlocksEditor.kt:3438`）→ `onSettle` → `controller.moveBlock(from, to)`（`BodyBlocksEditor.kt:3304`）：

```kotlin
fun moveBlock(from: Int, to: Int) {
    val move = MoveBlockCommand(...)
    move.apply(this)                                   // 换位
    extra += buildImageSeparatorCommands().onEach { it.apply(this) }  // 补空行
    pushExecuted(CompositeCommand(listOf(move) + extra))
}
```

**换位与补空行确实在同一帧、同一个 `moveBlock` 调用里完成**，两者之间没有"第二次提交"。

### 2.2 真正的元凶：库把 `onSettle` 放在落位滑行动画之后

依赖：`sh.calvin.reorderable:reorderable:3.1.0`（本地同版本副本：`Reorderable/reorderable/src/commonMain/kotlin/sh/calvin/reorderable/ReorderableList.kt`）。

`ReorderableListState.settle()`（该文件 **158-202 行**）：

```kotlin
internal suspend fun settle(i: Int, velocity: Float) {
    ...  // 计算 targetIndex
    draggingItemIndex = null
    if (targetIndex != null) {
        val offsetToTarget = ...
        itemOffsets[i].animateTo(offsetToTarget, animationSpec, initialVelocity = velocity) // ① 弹簧滑行（suspend，跑完才返回）
        onSettle(i, targetIndex)                                                            // ② 才回调我们
    } else {
        itemOffsets[i].animateTo(0f, animationSpec, initialVelocity = velocity)
    }
    animatingItemIndex = null
}
```

`animationSpec = spring(stiffness = Spring.StiffnessMediumLow)`（76-78 行），典型位移下 **300~500ms**。

于是时序是：

```
手指抬起 ──▶ ① 被拖块弹簧滑行（300~500ms，观感=换位完成）──▶ ② onSettle ──▶ 换位+空行同帧生效
                                                              ▲
                                                        空行在这一刻才出现
```

"换位"的视觉早已在 ① 演完，而空行要等到 ② —— 所以看起来永远是"先换位、后弹空行"。

### 2.3 关键约束：拖拽期间不能改列表

库的 `ReorderableColumn` 用 `remember(list, spacing)` 建状态（`ReorderableList.kt:389`），内部 `itemIntervals = MutableList(listSize)`、`itemOffsets = List(listSize) { Animatable(0f) }` **按构造时的 size 定长**。

因此：

- 拖拽中往 `blocks` 里插入空块（"提前补空行"）→ 列表结构变化 → `remember` 重建 → `draggingItemIndex` 丢失 + 新的 `itemIntervals` 越界风险 → **拖拽当场断掉**；
- 同理，"拖拽中插入占位块" / "拖拽开始时预插空行" 全部不可行。

> 结论：**唯一的解法是把"提交（onSettle）"提前到落位滑行之前**，即必须动到库的 `settle()`。

## 三、方案对比

| 方案 | 做法 | 同步效果 | 代价 / 副作用 |
| --- | --- | --- | --- |
| **A1（选定）提前提交 + 自接续滑行** | 把库 Column 版以 Apache-2.0 复制进 App，仅改 `settle()`：先 `onSettle` 提交（换位+空行同帧），再由 App 侧统一承接所有块的落位滑行 | ✅ 手指抬起瞬间：换位 + 空行同时生效；所有块从"落下瞬间的视觉位置"连续滑到新槽位，空行随邻居让位"展开" | 新增约 400 行 vendored 代码（带协议头与改动说明）+ 约 80 行滑行控制器 |
| A2 提前提交 + 直接吸附 | 同上复制，但不做接续滑行 | ✅ 同步 | 松手瞬间被拖块跳变（约半行~一行）；邻居若弹簧未跑完也会跳 |
| B 空行展开动画 | 不改库，落位后新空块做高度 0→一行动画 | ❌ 仍有先后，只是观感连续 | 改动最小，但不满足"同步"诉求 |
| C 拖拽期预留间隙 | 拖拽时给图片块预留一行高间隙，落位用真实空块接管 | 部分 | 未形成相邻时间隙收回→新增约一行抖动；且 item 高度变化会干扰库用高度算换位阈值 |

## 四、A1 详细设计

### 4.1 时序（改造后）

```
手指抬起
   │
   ├─ settle()：先抓取"落下瞬间每一项的视觉 Y"（布局 Y + 当前 offset）
   │
   ├─ 立即 onSettle(from, to)  ──▶ App: controller.moveBlock() ──▶ 换位 + 补空行（同一帧）
   │
   └─ 下一帧重排后：对每一项计算 startOffset = 落下视觉Y − 新布局Y，
      统一 snapTo(startOffset) → animateTo(0)（spring，带初速度）
      ⇒ 被拖块从手指位置滑到新槽位；被挤开的邻居继续滑完剩余行程；
        新插入的空块无历史位置 → 直接出现，空位由邻居让位"展开"出来
```

**为什么不是只滑被拖块**：拖拽中库会把"让位"的邻居也用弹簧平移 `±(size+spacing)`。若提交后直接丢弃这些 offset，邻居若弹簧未跑完会瞬跳。统一"谁有残留位移谁就接着滑到 0"可以一次解决被拖块与邻居两种残留。

### 4.2 新增文件

`app/src/main/java/com/corgimemo/app/ui/components/reorderable/BlocksReorderableList.kt`

- 复制自 `Reorderable/reorderable/src/commonMain/kotlin/sh/calvin/reorderable/ReorderableList.kt`（v3.1.0，Apache-2.0）；
- **保留原版权头**，并在文件头追加"改动说明"块（来源版本、改了什么、为什么），满足 Apache-2.0 的署名与变更声明要求；
- 包名 `com.corgimemo.app.ui.components.reorderable`；符号加 `Blocks` 前缀避免与库同名符号混淆；
- 裁剪：只保留 Column 相关（`ReorderableRow` / `ReorderableRowScope` 不复制）；
- `DragGestureDetector` 是库的 public API，直接引用 `sh.calvin.reorderable.DragGestureDetector`，不复制。

### 4.3 改动点（vendored 文件内）

1. **`BlocksReorderableListState.settle()`**：
   ```kotlin
   if (targetIndex != null) {
       // 【改动1】先抓取"落下瞬间"的视觉快照（Column 局部坐标）
       val snapshot = buildList {
           for (j in itemIntervals.indices) {
               add(GlideSnapshot(key = keyOf(j), visualTop = itemIntervals[j].start + itemOffsets[j].value))
           }
       }
       // 【改动2】先提交：App 在本帧内完成换位 + 补空行
       onSettle(i, targetIndex)
       // 【改动3】登记待接续滑行；不再在库内 animateTo（旧 state 会随列表变更被重建）
       glide.onCommitted(snapshot, velocity)
       // 【改动4】兜底：若调用方未改列表（state 未被重建），旧 offset 仍需回 0
       itemOffsets.forEach { if (it.targetValue != 0f) scope.launch { it.animateTo(0f, animationSpec) } }
   } else {
       itemOffsets[i].animateTo(0f, animationSpec, initialVelocity = velocity) // 原样
   }
   ```
2. **新增 `BlocksGlideController`**（vendored 文件内，`remember` 持有，跨 state 重建存活）：
   - `pending: Map<Any?, Float>`：key → 落下瞬间的视觉 Y（Column 局部）；
   - `anims: SnapshotStateMap<Any?, Animatable<Float, AnimationVector1D>>`：正在滑行的块；
   - `onCommitted(snapshot, velocity)`：写 `pending`；并起一个 2 帧后的清扫协程，丢弃无人认领的条目；
   - `consume(key, newLayoutTop)`：`pending.remove(key)` → `startOffset = visualTop − newLayoutTop` → `snapTo(startOffset)` → `animateTo(0f, spring(StiffnessMediumLow), initialVelocity)` → 结束后从 `anims` 移除；
   - `offsetOf(key): Float`：`anims[key]?.value ?: 0f`（在 `graphicsLayer` 里读，属于状态读取，会被观察）。
3. **`BlocksReorderableItem` 的 graphicsLayer**：
   ```kotlin
   .graphicsLayer {
       translationY = state.itemOffsets[index].value + glide.offsetOf(key)   // 拖拽期用前者，落位后用后者，互斥
   }
   .zIndex(if (isAnimating || glide.isGliding(key)) 1f else 0f)
   ```
4. **Column 上补 `onGloballyPositioned`** 记录 `columnTopInWindow`，使 `visualTop`（Column 局部）与 item 侧测到的 `positionInWindow().y` 可换算（两者差一个常量，可直接在 Column 侧统一换算成窗口坐标，App 侧无需感知）。
5. **item 侧测量**：在 `BlocksReorderableItem` 已有的 `onGloballyPositioned` 里，按 key 认领自己的 `pending` 条目（`glide.consume(key, coords.positionInWindow().y)`）。

### 4.4 App 侧改动（`BodyBlocksEditor.kt`）

- `BlocksReorderableColumn`（3425-3472 行）改用 vendored 的 `BlocksReorderableColumn`，**签名与 `onReorder` 语义保持不变**（震动 + `controller.moveBlock(from, to)` 原样保留）；
- 删除 `import sh.calvin.reorderable.ReorderableItem` / `ReorderableColumn` 在该文件的引用（避免同名符号歧义）；
- `itemKey = { it.id }` 保持不变（vendored 版依赖它做组合身份 + 滑行归属）。

`controller.moveBlock()`（`BodyBlocksEditor.kt:3304`）与 `buildImageSeparatorCommands()`（1750）**不改动**。

### 4.5 坐标系约定（易踩坑）

- 库内部 `itemIntervals[i].start` = item 相对 **Column** 的 `positionInParent().y`（**不含** graphicsLayer 平移——同节点上 `onGloballyPositioned` 报表布局位置）；
- item 侧 `coords.positionInWindow().y` = 窗口坐标（该文件已 import `positionInWindow`，见 4145 行用法）；
- 换算：`visualTopInWindow = columnTopInWindow + itemIntervals[i].start + itemOffsets[i].value`，其中 `columnTopInWindow` 由 vendored Column 的 `onGloballyPositioned` 维护；
- 拖拽期间 Column 顶部不动、列表不重排，故"落下瞬间快照"与"重排后测量"可直接相减。

## 五、边界情况

| 场景 | 处理 |
| --- | --- |
| 落位未形成图-图相邻（不补空行） | 正常：只有被拖块与让位邻居滑行，无新块 |
| 一次拖拽产生多处相邻 | `buildImageSeparatorCommands()` 自后向前插入，多插的空块没有历史位置 → 直接出现；邻居滑行把位置让出来 |
| 拖的是文本块 | 同样走统一滑行，行为一致 |
| 落位后列表未变化（`moveBlock` 早退） | `settle` 的兜底分支把旧 offset 回 0；`pending` 无项认领，2 帧后清扫 |
| 块在大列表外 / 已被移除 | `pending` 认领不到 → 2 帧后清扫，不残留 |
| `targetIndex == null`（没跨越任何项） | 保持库原行为：被拖块原地弹回 |
| 屏幕旋转 / 配置变更 | `BlocksGlideController` 在 composition 内 `remember`，重建后 pending 清空，等价于直接吸附（可接受） |
| 首帧闪动 | `onGloballyPositioned` 在 draw 前派发则同帧 snap，无闪动；若 Compose 版本把派发放到帧末，最多 1 帧（16ms）偏差 —— 需真机逐帧确认（见验证清单） |

## 六、自验证清单（真机）

1. **核心诉求**：两图相邻拖拽 —— 松手瞬间应同时看到"图归位"与"空行出现"，中间**无停顿**；录屏逐帧看松手后 0~3 帧内空行已在位。
2. **滑行连续性**：松手后被拖块应从手指位置平滑滑到槽位；被挤开的邻居若弹簧未跑完，应继续滑完而**不瞬跳**。
3. **图片不重载**：交换后图片不应重新加载（itemKey 锚定仍在），无高度塌陷回弹。
4. **无残影/无卡住**：连续快速拖拽 10 次以上，不应出现某块停在偏移位置不回位。
5. **撤销**：一次拖拽 = 一条撤销记录；撤销后顺序 + 补的空行一起回退，再重做仍一致。
6. **落位未相邻**：图拖到两段文字之间 —— 不补空行，无多余空行，无异常跳动。
7. **跨类型**：文本块拖拽、复选框块拖拽、分割线块拖拽均正常滑行。
8. **保存**：拖拽后 `onDocChanged` 触发，退出重进顺序与空行保持。
9. **未形成相邻时不残留间隙**、滚动容器下拖拽（位置换算）正常。
10. 回归：首页时间线等其它用到 `sh.calvin.reorderable` 的位置（设置类列表 `ReorderableColumn`）**不受影响**（仍用库原版）。

## 七、风险与回滚

- **风险 1（主要）**：vendored 代码与库后续版本脱钩。缓解：文件头写明来源版本与改动，且只改 `settle()` 一处语义 + 新增 glide 层，其余原样复制；将来升级库时按同一 diff 重新应用。
- **风险 2**：`onGloballyPositioned` 派发时机导致 1 帧闪动。缓解：若实测有闪动，可退一步改为"提交前用 `offsetToTarget` 解析式估算起始位移"或在滑行未起前保持 `zIndex` 抬升（不改布局）；最坏情况退到方案 A2（直接吸附）。
- **风险 3**：`Animatable` 泄漏。缓解：滑行结束即从 `anims` 移除；`pending` 2 帧清扫；`rememberCoroutineScope` 随 composition 取消。
- **回滚**：`BodyBlocksEditor.kt` 只需把 `BlocksReorderableColumn` 换回 `sh.calvin.reorderable.ReorderableColumn`（改动局限在 3425-3472 行的一个函数），vendored 文件删掉即可，数据层与命令栈零改动。

### 与方案文档的差异

- 滑行控制器不放在 `BodyBlocksEditor.kt` 而放在 fork 文件内 —— 它需要 item 的测量回调与 state 的 `itemIntervals`，放在一起内聚性更好；App 侧接口保持"用法与原库完全一致"。
- 新增两项计划外细节：`startDrag()` 时 `glide.cancelAll()`（防拖拽位移与滑行位移叠加）；`pending` 两帧后清扫未认领项。

### 待真机验证（重点三项）

1. 松手瞬间"换位 + 空行"是否同帧出现（核心诉求）；
