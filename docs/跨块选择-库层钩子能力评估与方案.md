# 跨块选择：库层钩子能力评估与方案

> 2026-09-11 · 基于本地 fork `compose-rich-editor/richeditor-compose` 的调研结论与后续方案对比。

## 一、调研结论：库内没有现成的跨块选取方法

| # | 证据 | 位置 |
|---|------|------|
| 1 | `RichTextState.selection` 是单一 `TextRange`，只能表达单编辑器内部选区 | `RichTextState.kt:233` |
| 2 | 全库无 `crossBlock / multiBlock / 跨块` 任何机制；`SelectionContainer` 仅用于 sample 只读展示 | 全库 grep |
| 3 | 公共选区 API 全部基于单块 TextRange（`removeSelectedText` 900、`replaceSelectedText` 940、`getSpanStyle(textRange)` 1019 等）；无 selectAll | `RichTextState.kt` |
| 4 | 库内注释自证手柄是独立 Popup：*"the selection handles are separate popups"* | `RichTextState.kt:682` |
| 5 | `selectionGesture*` 手势机制 + `adjustGestureSelection` 几何钳制全部服务于单编辑器内部 | `RichTextState.kt:678-706 / 5130` |

**结论**：跨块选区的「状态模型 + hitTest + 富文本拼接」只能在库外编辑器层自研（现有 `CrossBlockSelection` 控制器方向正确）；痛点集中在「原生手柄拖动无法跨块延伸」。

## 二、信号链分析（改库的理论基础）

原生手柄拖动期间，编辑器层能/不能看到什么：

| 信号 | 可见性 | 说明 |
|------|--------|------|
| selection 变化 | ✅ 可见 | 手柄拖动 → 平台更新 `textFieldValue` → `onValueChange`（`BasicRichTextEditor.kt:384`）→ `state.selection`（public var，`snapshotFlow` 可观察，**无需改库**） |
| 手势活性 | ✅ 可见 | `isSelectionGestureLive()`（5119）；Android 上 `treatSelectionChangesAsGesture` 恒 true |
| 指针位置 | ❌ 盲区 | 手柄 Popup 挡住事件，编辑器 Initial pass 观察器（`BasicRichTextEditor.kt:418`）收不到任何指针 |
| 出界后拖动 | ❌ 全盲 | selection 被 foundation clamp 在 `[0, length]`，**不再变化**；无按压信号（Press/Release 属于长按那一次，早已结束） |

**钩子能导出的**：selection 变化流（已可观察）、手势活性状态（internal→public 小改）、`textLayoutResult`/`textFieldWindowPosition` 公开（小改）、「选区端点贴边」事件回调（中改）。
**钩子永远给不了的**：手柄 Popup 的触摸事件、编辑器区域外的指针位置——Popup 子窗口架构决定，Google 侧无解。

## 三、方案对比

### 方案 I：选区上按压拖动延伸（跟手，推荐）

- **交互**：长按选词出选区 → 抬手 → **再按在选区文字上并拖动** → 进入跨块延伸（跟手）。
- **可行性**：按压/移动事件全在主窗口编辑器内，`blockLayouts` + `hitTest` 基建直接复用；与「长按直接拖」入口（不抬手）、原生手柄（块内微调）三入口互不冲突。
- **库层改动**：基本无需（可选：公开 `textLayoutResult`）。
- **冲突处理**：系统原生「点一下选区」是唤工具栏（轻点）；我们只在「按住 + 移动超过 slop」时接管，轻点放行。需 Initial pass 观察保零消费。
- **优点**：跟手、无手绘、原生手柄样式原样保留（用户要求「完全复用原生样式」继续成立——手柄就是原生手柄）。

### 方案 H：贴边停驻自动步进（不跟手，可作为 I 的补充）

- **交互**：拖原生手柄到块底/顶边 → 端点贴边停住 → 停驻约 300ms 后自动逐行步进（跨块延伸）。
- **停止条件**：selection 重新变化（拖回块内）/ 新按压 / 无信号超时衰减（约 600ms 无变化即停）/ 工具栏弹出。
- **库层改动**：「端点贴边」检测编辑器层自己能算（bbox + selection），无需改库；改库只是让事件更精确。
- **缺点**：不跟手；抬手不可见 → 只能靠超时收敛，手停住时可能多延伸几行；速度感需打磨。
- **优点**：让「手柄拖出边界」这个直觉动作有一半可用性（意图被翻译成自动延伸）。

### 方案 K：库内自绘手柄替换 foundation 手柄

用户已明确禁止（「别手绘拖拽手柄了」），仅记录不展开。且 foundation 手柄无公开禁用开关，需 fork 深改 `BasicTextField` 行为，工程量与风险最大。

## 四、推荐与实施步骤（方案 I 为主）

1. 编辑器层新增「选区按压拖动」入口：跨块/块内选区激活时，`pointerInput` Initial pass 观察按压点落入选区包围盒 → 移动超 slop → 接管为延伸手势（复用第九轮 `started` 延伸路径）。
2. 轻点选区仍走系统原生行为（工具栏），零消费放行。
3. 原生手柄保持块内微调职责不变，样式零改动。
4. （可选叠加）方案 H 贴边步进：待 I 落地实测后再评估是否需要。

## 五、风险与未知

- 方案 I 的「按住选区拖动」与原生「长按选区再选词」的竞态：需要长按 grace 窗口（已有 `CROSS_LONGPRESS_GRACE_MS` 机制）继续生效。
- 方案 I 与「长按直接拖」入口的手势状态机需合并审查，避免两个 `started` 路径互相踩踏。
