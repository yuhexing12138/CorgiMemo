# 灵感编辑页正文「换行不新建块」技术方案

> 目标页面：灵感编辑页正文编辑区（`BodyBlocksEditor`，路线 4 块架构）
> 产出日期：2026-09-15
> 状态：方案待评审（未动代码）
> 关联文档：`docs/路线4-块级图片-实施方案.md`（块架构总纲，其中第 108/239 行曾讨论"块内 Enter 是否拆块"，当时结论为**拆块**，本方案是对该决策的**反向修订**）

---

## 一、需求与已确认决策

用户诉求：**在正文文本中换行时不要新建块。**

经两轮确认，最终决策如下（均为用户明确选择）：

| # | 决策项 | 结论 |
|---|--------|------|
| 1 | 适用块范围 | **普通段落 + 列表 + 复选框**，全部块内换行；不因换行产生新块 |
| 2 | 空行（连续两次回车） | **空行也留在同一块内**（接受"保存后重进会被还原成两个块"的代价，见 §5.1） |
| 3 | 粘贴多行 | **与回车保持一致**，粘贴多行不拆块 |
| 4 | 视觉一致性（硬约束） | **修改后文本视觉呈现必须与修改前一致** |
| 5 | 复选框实现路线 | **改造 compose-rich-editor 库**，参考列表（`UnorderedList`）的段落级实现，让复选框支持块内换行、每行一个勾选框 |

> 决策 4 与决策 5 是一组强绑定：勾选框现状是 **App 块级属性 + 块级渲染**（整块左侧只有一个图标），若只在 App 层取消拆块，块内多行会共用一个勾选框，视觉必然不一致。因此必须把复选框下沉为**库的段落级类型**。

## 二、现状链路分析

### 2.1 回车拆块的两条独立路径

| 路径 | 入口 | 代码位置 | 行为 |
|------|------|----------|------|
| 硬键盘 | `onPreviewKeyEvent` 拦截 `Key.Enter` | `BodyBlocksEditor.kt` L4447-4451 | 吞掉事件，调 `splitTextBlockAtCursor`（`\n` **不进入文本**） |
| 软键盘 | 内容 observer 检测 `text.contains('\n')` | L4294-4302 | 调 `normalizeBlockParagraphs`，按 `\n` 拆行成多个块 |

两条路径最终都落到 **`ReplaceBlocksCommand`**（removed = 源块全文，inserted = 前半块 + 后半块），进入块级撤销栈。

硬键盘拆块主线：`splitTextBlockAtCursor`（L2729）→ `splitTextBlock`（L2742）。拆块前有三条前置分支：

- 空缩进行回车 = 减一级缩进（`dedentBlockAtContentStart`，原地不拆块）；
- 空复选框项回车 = 退出复选框（整块替换为普通空块）；
- 空列表项回车 = 退出列表 / 降一级（`exitListOrDedentEmptyListItem`，L2681）。

软键盘路径 `normalizeBlockParagraphs`（L2897）有同款前置分支，之后按行拆块，并负责列表类型 / 层级 / 复选框态 / 缩进档位的**属性继承**（新块 `checked = false`、`indentLevel` 继承、`listLevel` 继承）。

### 2.2 持久化往返链路（本就支持块内多行）

这是本方案最重要的既有事实——**"块内多行"在数据层是原生支持的，不需要改持久化格式**：

| 环节 | 实现 | 结论 |
|------|------|------|
| 库序列化段落 | `RichTextStateMarkdownParser.decode` L551-553：段落间 `builder.appendLine()` | 块内多段落 → **单 `\n`** 连接 |
| 库反序列化 | `RichTextState.kt:5520` `RichTextStateMarkdownParser.encode(markdown)` | 单 `\n` → 多段落（软换行） |
| App 整篇组装 | `toMarkdown()` L1604：`blocks.map{...}.joinToString("\n\n")` | 块间 **`\n\n`** |
| App 加载 | `initialize` L1434-1440：Text 段按 `\n\n` 拆段建块 | 注释原文：**「单 `\n` 的软换行保留在块内」** |
| 阅读卡展示 | `InspirationViewCard.kt` L422：`contentFormat.split("\n\n")` | 段内 `\n` 交给库渲染 → **换行不丢** |

因此：`块内换行 = 单 \n`、`块间 = \n\n`，两层语义正交，**取消拆块不会破坏往返**。

### 2.3 视觉：块间距 = 块内行距（改动视觉影响极小的依据）

`BodyBlocksEditor.kt` L4343-4355 注释明确：编辑器 `minHeight = 0.dp` + `contentPadding` 垂直 = 0，且 L4352 原文——

> 视觉上"两块文本之间的行距"与"块内两行之间的行距"**完全相同**。

即取消拆块后，**编辑态的换行视觉零变化**，唯一变化是：不再产生新块（不再多出拖拽手柄、不再产生块级撤销条目）。

### 2.4 复选框与缩进为什么是"坏"的（问题根因）

| 属性 | 现状承载方式 | 块内换行是否天然成立 |
|------|--------------|----------------------|
| 列表 marker | **库的段落级类型**：`UnorderedList.startRichSpan`（L110-140 生成 `"• "`）+ `ParagraphStyle(TextIndent)` | ✅ 成立。库在插入 `\n` 时 `richSpan.paragraph.slice(...)`（`RichTextState.kt` L3802）**新段落继承段落类型**，并把 `newParagraph.type.startText` 写回文本（L3855），所以块内每行都有自己的 bullet |
| 复选框 | **App 块级属性** `BodyBlock.Text.checked: Boolean?`，由 `BlockTextItem` 的 `Row` 左侧渲染**一个** `CheckboxBoxIcon`（L4396-4404） | ❌ 不成立。块内多行共用（且仅有一个）勾选框 |
| 缩进 | **App 块级属性** `BodyBlock.Text.indentLevel`，走布局级 start padding（EM 前缀作 markdown 载体） | ✅ 成立（整块缩进，块内每行继承） |

**结论：只有复选框需要下沉到库。**

## 三、方案总览

分三个阶段，**A 与 B 必须同期上线**（B 依赖 A 的段落级复选框，否则取消拆块后复选框视觉崩），C 为收尾适配。

```
阶段 A（库）  新增段落级复选框类型 TaskList
              ├─ 类型与 marker（startRichSpan + RichSpanStyle.CheckBox）
              ├─ 渲染：drawCustomStyle 画 18dp 圆角框 + 对勾（编辑态/只读态统一）
              ├─ markdown：编码 "- [ ] " / "- [x] "，解码识别前缀
              ├─ 插入 \n 时继承类型（复用既有 slice 机制，勾选框默认未勾选）
              └─ 点击切换 checked 的能力（库 API 或 App 命中测试）
                       │
阶段 B（App） 取消拆块                          │
              ├─ 硬键盘 Enter：改为在光标插入 \n（不再拆块）
              ├─ 软键盘 observer：不再按行拆块
              ├─ 粘贴多行：不再拆块
              ├─ 复选框：块级 checked → 段落级（读/写/切换全部改道）
              └─ 清理/移交空列表项、空复选框项回车分支（可交库 config）
                       │
阶段 C（适配） 下游链路
              ├─ initialize：多行段（含列表/复选框）加载适配
              ├─ InspirationViewCard：多行复选框段渲染
              ├─ plainText / 字数统计 / 复制全文
              ├─ 历史数据兼容（存量 markdown 前缀不变，天然兼容）
              └─ 撤销粒度、图片载体不变量回归
```

## 四、详细设计

### 4.1 阶段 A：库新增段落级复选框 `TaskList`

#### 4.1.1 类型定义（以 `UnorderedList` 为模板）

```kotlin
// paragraph/type/TaskList.kt（新增）
internal class TaskList private constructor(
    initialIndent: Int = DefaultListIndent,
    startTextWidth: TextUnit = 0.sp,
    initialLevel: Int = 1,
    initialChecked: Boolean = false,   // 段落级勾选态（本方案新增）
) : ParagraphType, ConfigurableStartTextWidth, ConfigurableListLevel
```

要点：

1. **`startRichSpan` 的文本 = 空白占位**（不是 `[ ]` 字面量），宽度由 `startTextWidth` 控制，勾选框由 `drawCustomStyle` 画——这样视觉可达"与现状 `CheckboxBoxIcon` 一致"，而不是退化成 Unicode `☐` 字符；
2. `level` 沿用 `ConfigurableListLevel`，缩进公式与 `UnorderedList` 相同（`(indent * (level - 1))`）；
3. `getNextParagraphType()` 返回**未勾选**的新 `TaskList`（对应现状"回车新行 = 未勾选复选框项"）；
4. `copy()` / `equals` / `hashCode` 必须包含 `checked` 字段（否则库的 span 合并、状态比较会丢勾选态）；
5. `checked` 变更时需要触发 `startRichSpan` / style 重算（参考 `level` 的 setter 写法）。

#### 4.1.2 渲染：勾选框用 `drawCustomStyle` 绘制

在 `RichSpanStyle` 中新增（或复用 `TaskList` 自带的 span style）：

```kotlin
// model/RichSpanStyle.kt 内新增
public class CheckBox(
    public val checked: Boolean,
    private val size: TextUnit = 18.sp,
    private val cornerRadius: TextUnit = 5.sp,
    private val strokeWidth: TextUnit = 1.5.sp,
    private val backgroundColor: Color,   // 勾选态填充（App 传主题 primary #FF9A5C）
    private val strokeColor: Color,       // 未勾选态描边（onSurfaceVariant）
    private val checkColor: Color,        // 对勾（白）
) : RichSpanStyle
```

`drawCustomStyle` 内用与 `Code`（`RichSpanStyle.kt` L109-140）相同的方式取该 span 的 `getBoundingBoxes`，在首行位置画：

- 未勾选：圆角矩形描边（1.5dp）；
- 已勾选：圆角矩形填充 + 白色对勾（用 `Path` 画两段折线，等价于 `Icons.Default.Check`）。

**为什么可以这么做**：`drawRichSpanStyle` 同时挂在编辑态（`BasicRichTextEditor.kt:400`）与只读态（`BasicRichText.kt:79`），绘制走 `DrawScope`，不需要 `BasicTextField` 支持 inline content（这正是图片当初被迫走覆盖层的原因，复选框不需要位图解码，因此不必走那条复杂路径）。

> ⚠️ **实测发现的前置条件（实施阶段补充）**：`RichTextState.styledRichSpanList` **只收集段落 children**，而段落 marker（`startText`）是在 `updateAnnotatedString` 里用 `append(type.startText)` 直接拼进文本的（`RichTextState.kt:2865-2872`，只带 `SpanStyle`，不走 children 的收集回调）。因此挂在 marker 上的 `RichSpanStyle` **不会**被 `drawRichSpanStyle` 遍历到——必须在 `ui/ModifierExt.kt` 的 `drawRichSpanStyle` 里**额外遍历 `richParagraphList`，对 marker 样式非 Default 的段落补一次 `drawCustomStyle` 调用**。否则勾选框不会画出来（本方案实施时已按此路径落地）。

**几何约定（实施细化）**：勾选框尺寸用 `TextUnit`(sp) 而非 `Dp`——因为 `startTextWidth` 由库在排版后按 `TextUnit` 测量回填（`RichTextState.kt:4869/4903`），`TaskList` 的 `TextIndent` 也必须是同一单位体系。段落 marker 被 `TextIndent(firstLine = restLine = 缩进 + 预留宽)` 推到「勾选框 + 间距」之后，勾选框绘制在 marker 左侧的预留区里（左缘 = marker 左缘 − 预留宽）。

#### 4.1.3 markdown 编解码

编码（`RichTextStateMarkdownParser.appendParagraphStartText` L722-742 增设分支）：

```kotlin
is TaskList ->
    append("  ".repeat(type.level - 1) + if (type.checked) "- [x] " else "- [ ] ")
```

解码（`encode` 的 `PARAGRAPH` / `LIST_ITEM` 钩子区域，L140-209）：

- 若解析器产出 GFM task-list 节点 → 用 AST 判定；
- 否则退化为**文本前缀判定**（与 App 现状 `checkboxMarkdownInfo` 一致）：`LIST_ITEM` 内容以 `[ ] ` / `[x] ` 开头即可识别，剥前缀后 `checked` 入段落类型；
- 层级仍取「源码行首缩进 ÷ 2」（与列表同款，L177-189）。

> **重要兼容性红利**：App 现在输出到 markdown 的就是 `- [ ] ` / `- [x] `，所以**持久化格式零变更**，存量数据天然可被库解析，无需数据迁移。

#### 4.1.4 点击切换勾选

两种可选路径（实现阶段定稿，建议先 ②）：

1. **库内提供命中测试 API**：把"点击位置 → 所属段落"的判定封装到库（`getRichSpanByTextIndex` 已把 `startText` 计入坐标，L49-97）；
2. **App 侧命中测试**（改动面小、风险低）：编辑页在文本容器上挂 `pointerInput`，把点击点换算成文本 offset（`layoutResult.getOffsetForPosition`），判断是否落在某段落 `startRichSpan` 的 range 内 → 切换该段落 `checked`。只读态（阅读卡）同理由卡片自己做。

### 4.2 阶段 B：App 取消拆块

#### 4.2.1 硬键盘 Enter（L4447-4451）

改为：在光标处插入 `\n`，不拆块。

```kotlin
Key.Enter, Key.NumPadEnter -> {
    // 回车 = 块内换行（不再拆块）；列表/复选框的 marker 由库按段落类型自动续
    block.state.addTextAfterSelection("\n")
    // 勾选态文字视觉降级等由既有 observer 链路处理
    true
}
```

注意：
- 保持"吞掉事件"（`return true`），避免系统再插入一次 `\n`；
- 撤销走**块内 history**（库），不再进块级命令栈——这是本方案的**预期变化**，需在验收时确认可接受。

#### 4.2.2 软键盘（observer，L4294-4302）

`when` 中 `text.contains('\n') -> controller.normalizeBlockParagraphs(block)` 需要**不再按行拆块**。处理方式：

- 普通段落：**直接放行**（`\n` 留在块内，什么都不做）；
- 列表 / 复选框段落：同理放行（库插入 `\n` 时已自动继承段落类型并续 marker）；
- 空列表项 / 空复选框项回车：**移交库的 `config.exitListOnEmptyItem`**（L3817 已实现），或保留 App 的等价判定但改为"就地改段落类型"而非拆块；
- 空缩进行回车：保留 `dedentBlockAtContentStart`（原地减缩进，本来就是不拆块的分支）。

`normalizeBlockParagraphs` 与 `splitTextBlock`（及其 `exitListOrDedentEmptyListItem` 等）在改造后**不再被 Enter 调用**，建议：

- 保留函数但标记 `@Deprecated`（或直接删除，视回归结果定），避免留下"两套语义"；
- `ReplaceBlocksCommand` 的拆块能力本身仍需保留（图片 / 分割线 / 块重排等命令仍用它）。

#### 4.2.3 粘贴多行

`normalizeBlockParagraphs` 同时承担粘贴多行的拆块。取消后粘贴多行会留在同一块内，与回车一致（决策 3）。需注意粘贴内容若自带空行（`\n\n`），会命中 §5.1 的边界。

#### 4.2.4 复选框：块级 → 段落级

| 环节 | 现状 | 改造后 |
|------|------|--------|
| 数据 | `BodyBlock.Text.checked: Boolean?` | 由块内 `RichTextState` 的段落类型承载（库 `TaskList`） |
| 渲染 | `BlockTextItem` 的 `Row` 左侧 `CheckboxBoxIcon`（L4396-4404） | 移除块级图标，改由库 `drawCustomStyle` 逐段落绘制 |
| 文字降级 | `block.checked == true` → 文字 40% 透明（L4502-4506） | 改为按段落 span 透明（库 span style 或 App 后处理） |
| 切换 | `controller.toggleCheckboxChecked(block.id)` | 点击段落 → 切换该段落 `checked` |
| markdown | `checkboxMdPrefix` 拼前缀（`toMarkdown` L1558-1573） | 交给库（格式不变，`- [ ] `/`- [x] `） |
| 加载 | `checkboxMarkdownInfo(trimmed)` 剥前缀建块（L1460-1469） | 交给库解析为 `TaskList` 段落 |
| 缩进 | `plainIndentPrefix(indentLevel)` EM 载体 | 可继续保留（App 布局级），或一并移交库 `level`（见 §7 可选项） |

#### 4.2.5 空行与"退出列表"语义

## 五、风险与边界

### 5.1 块内空行 `\n\n` 与块间分隔符冲突（**最高优先级风险**）

- **成因**：块间分隔符与"块内空行"在 markdown 里都是 `\n\n`，无法区分；
- **表现**：块内留空行 → 保存 → 重进编辑页 → 该处被还原成**两个块**（往返不一致）；
- **视觉影响**：因为"块间距 = 块内行距"（§2.3），**视觉上仍然无差异**，只是块结构变化；
- **用户已确认接受**（决策 2）。若后续希望消除，可选缓解：
  - 方案 a：块内空行序列化为 `<br>`（库的 HTML 分支已有 `isFromLineBreak` 机制，解码侧需确认支持）；
  - 方案 b：块内空行序列化为 NBSP 占位行（复用 `EMPTY_BLOCK_PLACEHOLDER` 思路）；
  - 方案 c：维持现状（接受结构漂移）。
- **注意**：方案 a/b 都需要在 `toMarkdown` / `initialize` 两侧成对处理，且要覆盖阅读卡渲染路径。

### 5.2 多行列表 / 多行复选框的加载往返

- 现状加载对"单行列表段"做了 `stripListLevelPrefix` + `setListMarker` 的层级修复（L1470-1487），注释记录了**≥4 空格的层级前缀会被 CommonMark 当成缩进代码块**的坑；
- 块内多行后，同一个块内可能出现 `  - a\n  - b`（多级、多行），**必须验证**：库对多行段能否正确还原层级；不能，则加载侧需逐行处理。

### 5.3 有序列表编号

- 库内部会按段落重新编号（`RichTextState.kt` 的 renumber 逻辑）；
- App 另有跨块 `renumberOrderedBlocks()`；
- 块内多段落编号由库负责后，**需确认跨块连续编号（块 A 的末项 → 块 B 的首项）是否仍然连续**，否则出现"1. / 2."后接"1."。

### 5.4 图片载体空块不变量

- 现状有严格的"图片载体空块"不变量与归一化（`InsertImageSeparatorCommand` / `normalizeImageSeparators`），判据与"块是否空白"强相关；
- 回车不再产生新块后，用户在载体空行里按回车 → 块内变成 `ZWSP + \n`，`isEffectivelyBlankLine` 仍判为空白（标记不会被误清），但**需回归验证**：归一化不会删除用户刚回车出的空行。

### 5.5 撤销粒度变化

- 回车从"块级命令（可整块撤销）"变为"块内 history"（逐字符粒度）；
- 用户连续回车后按 Ctrl+Z 的行为会与现状不同，需要在验收时确认可接受。

### 5.6 `plainText` / 字数统计 / 复制全文

- 块内多行后，这些路径按行或按块输出的逻辑都要复核，避免内容重复或丢失。

### 5.7 存量历史数据

- 低风险：markdown 格式（`- [ ] ` / `- [x] ` / 单 `\n` / `\n\n`）**完全不变**；
- 需要确认的是：旧数据里"每行一个块"的结构，重进后仍是每行一个块（因为旧数据是 `\n\n` 分隔），只是**之后编辑时**新换行才会块内合并——这是可接受的渐进行为。

## 十、补充需求：相邻文本块自动合并（v2026-09-15）

**需求**：当文字块相邻时，自动合并为一个块。

**为什么需要**：取消拆块后「块 = 一段连续文本」，但旧数据是"每行一个块"（块间 `\n\n`
分隔），删图 / 删分割线 / 拖拽重排也会留下相邻文本块——与模型不符，故统一收敛。

**用户确认口径**：

| 决策 | 结论 |
|------|------|
| 时机 | **加载 + 运行时**：打开旧笔记时合并；运行时任何**用户操作**后（`executeAndPush` / `executeAndPushWithImageSeparators`）也跑归一化 |
| 缩进差异 | **合并后保留缩进** → 转写为块内该行行首 EM 前缀（信息不丢；渲染为**可见宽空格**而非真缩进——块缩进是块级布局属性，块内无法逐行缩进） |
| 撤销 | 加载时的合并**不进命令栈**（属加载规范化，否则一进页面就能撤销回旧结构）；运行时的合并随触发操作打包成一步撤销 |

**实现要点**（`BodyBlocksEditor.normalizeAdjacentTextBlocksInto`）：

1. 先切出「连续文本块段」（被图片 / 分割线 / **载体空块**阻断），再**倒序**生成
   `ReplaceBlocksCommand`——倒序保证前面的段合并后不会让后面段的 index 失效
   （各段删除的块数不同）。
2. **接缝用单 `\n`**：与"回车不拆块"同一语义。**不能写 `\n\n`**——那是块间分隔符，
   写进块内在下次加载时会被重新拆开（等于没合并）。
3. 合并块继承**首块**的 id 与缩进档位；非首块的缩进差异转写成该行行首 EM 前缀。
4. 焦点：若原本落在段内某块，按「有效字数」换算到合并块内的对应偏移（与
   `mergeTextBlocks` 同款口径）。
5. 载体空块（`isImageSeparator`）**不参与合并**：图片相邻语义依赖它独立存在。
6. ⚠️ **undo / redo 不经过 `executeAndPush`**，所以撤销不会被立刻又合并回去。

**配套**：`effectiveText` 增剥 `PLAIN_INDENT_CHAR`（EM）——转写的缩进前缀是纯排版载体，
不应污染字数统计 / 复制全文 / 空行判定。

**已知取舍**：转写的 EM 前缀会作为**文本字符**留在块内（渲染为宽空格），且不能被
`plainIndentLevelOfMd` 识别为缩进（它只看段首）；往返稳定、信息不丢，但视觉上不是缩进。
