# 灵感编辑页「面板展开期间抑制软键盘」方案

- 日期：2026-09-21
- 范围：灵感编辑页（`InspirationEditScreen`）底部工具栏「T 字体面板」「Aa 字号颜色面板」
- 相关组件：`BlockNoteEditorWebView`（正文 WebView）、`RichTextEditor`（顶部标题）

## 1. 需求

底部工具栏的「T」（字体面板，`FontPickerPanel`）与「Aa」（字号颜色面板，`FontSizeColorPanel`）
展开后，这两个面板**以「软键盘高度」占据键盘位**（面板高度 = 最近一次记录的键盘高度，见
`InspirationEditBottomBar` 的 `keyboardHeight`）。

此时若用户在**正文中聚焦光标 / 多选**，Chromium 会请求软键盘，产生两个问题：

1. 键盘弹出把面板向上顶走，面板显示位置被破坏；
2. WebView 视口被压缩，与 `setEditorMinHeight` 的 `onSizeChanged` 下发互相激发，
   正是 v1.11.9 记录的「视口坍缩到一行高」的正反馈源头。

**目标**：面板展开期间，用户在正文中点击定位光标、长按选词、拖动选择手柄等操作**照常可用**，
但**不得唤起软键盘**。

## 2. 方案总览

### 2.1 状态来源

新增一个派生状态，统一表达「键盘让位给面板」这一中间态：

```kotlin
val isFormatPanelOpen = isFontPanelExpanded || isSizeColorPanelExpanded
```

两个面板**互斥占同一槽位**，且互斥切换在同一个点击回调内完成（同一帧快照），
因此该派生值不会在两个面板切换的瞬间闪出 `false`。

### 2.2 正文 WebView：四层抑制

| 层 | 手段 | 作用 |
| --- | --- | --- |
| 1 | `hideSoftInputFromWindow` | 抑制开启瞬间收掉可能已弹出的键盘 |
| 2 | `onCreateInputConnection` 返回 `null` | 输入法拿不到输入连接，不建立编辑会话 |
| 3 | `onCheckIsTextEditor` 返回 `false` | 系统输入法框架不再视其为可输入控件 |
| 4 | 页面注入 `inputmode="none"` | Chromium 官方支持的键盘抑制语义（Web 侧"自绘键盘"应用的标准做法） |

第 2、3 层由 `private class ImeSuppressibleWebView : WebView` 覆盖实现；
第 4 层由 `IME_SUPPRESS_SCRIPT` 注入，脚本用 `MutationObserver` 在抑制期间持续给
新出现的可编辑节点补标，解除时按 `data-ime-prev` 精确还原原值。

**为什么要四层**：Android WebView 的软键盘由 Chromium（AwContents）**主动请求**，
原生拦截只能让输入法拿不到输入连接，个别 ROM / 输入法仍会把面板拉起来；
`inputmode="none"` 则让浏览器自己不请求键盘。两道方向不同，互为兜底。

### 2.3 顶部标题：消费指针事件

标题是 Compose 的 `RichTextEditor`（BasicTextField），无法从 IME 层面拦截，改为
**面板展开期间消费指针事件**：

```kotlin
.then(
    if (isFormatPanelOpen) {
        Modifier.pointerInput(Unit) {
            awaitPointerEventScope {
                while (true) {
                    awaitPointerEvent(PointerEventPass.Initial).changes.forEach { it.consume() }
                }
            }
        }
    } else Modifier
)
```

- `PointerEventPass.Initial` 阶段事件**由父流向子**，BasicTextField 的点击定位手势走
  `Main` 阶段，拿不到事件 ⇒ 不聚焦 ⇒ 自然不弹键盘。
- **刻意不使用 `enabled = false`**：那会连带把文字 / 占位符切成禁用色，并强行清掉已有焦点；
  本写法视觉零变化，代价只有展开 / 收起各一次 modifier 结构切换。

## 3. JS 注入的三个时机（缺一不可）

| 时机 | 覆盖场景 | 所在线程 |
| --- | --- | --- |
| `isImeSuppressed` 变化 | 用户手动展开 / 收起面板，即时生效 | UI 线程（`AndroidView.update`） |
| `WebViewClient.onPageFinished` | 页面重载后标记丢失 | UI 线程 |
| 桥 `ready` 上行后 | 编辑器 DOM 此时才真正挂载（进页即展开面板的场景） | UI 线程（上行消息入口已统一 post） |

⚠️ `evaluateJavascript` 等 WebView 方法只能在 **UI 线程**调用。`handleUpMessage` 由 JS 经
`@JavascriptInterface` 调用、运行在 WebView 的 Java 桥线程，因此**入口处就把整条消息
`mainHandler.post` 到主线程**再解析（v2026-09-21 起）——后续任何分支都不必再单独 post，
也不会踩「忘了切线程」的坑（详见第 9 节踩坑记录）。

## 4. 交互约定

- **保留光标与选区**：抑制只屏蔽 IME，点击定位光标 / 长按选词 / 拖动手柄多选全部保留；
  WebView 的选区由自身触摸手势与渲染层承担，与 IME 无关。
- **不主动弹回键盘**：面板收起后仅恢复"可唤起"能力，键盘由输入框焦点决定——
  用户再点一次正文 / 标题即恢复输入（与原有面板收起行为一致）。
- **锁定态不受影响**：`isLocked` 走既有 `setReadOnly` 通道。

## 6. 真机验证步骤

0. **先回归装载**：进入一条已有内容的灵感，正文应正常渲染（不出现「正在装载…」卡死）；
   若卡住，看 logcat 是否有 `bad up message` 异常栈（见第 9 节）。
1. 进入灵感编辑页，点 `⋮` 展开格式工具栏。
2. 点 `T` 展开字体面板（面板占据原键盘位、键盘收起）。
3. **点正文任意位置**：预期光标出现、**键盘不弹**、面板位置不动。
4. **长按正文选词 / 拖动选择手柄**：预期选区正常、**键盘不弹**。
5. 在选区状态下点面板里的字号 / 颜色项：预期样式即时生效（格式命令经 Bridge 下发）。
6. 点标题框：预期无反应、不弹键盘。
7. 点面板头「完成」收起面板，再点正文：预期键盘正常弹出（可唤起能力已恢复）。
8. `Aa` 面板重复步骤 2–7。
9. 两张面板互切（T → Aa）：预期面板不闪、键盘始终不弹。

**logcat 判据**（`adb logcat -s BlockNoteEditor:V`）：

- 展开面板时出现 `ime suppress = true`；收起时出现 `ime suppress = false`。
- 若键盘仍尝试弹出，会出现 `onCreateInputConnection: suppressed`（说明第 2 层生效）。

## 7. 回退点

若个别 ROM 上出现「选择手柄 / 浮动工具条异常」，把 `ImeSuppressibleWebView` 中
`onCreateInputConnection` 与 `onCheckIsTextEditor` 两个 override 注释掉即可，
退到「JS `inputmode` + 主动隐藏键盘」两道，焦点与选区完全走原生默认路径。

## 8. 已知边界

- `inputmode="none"` 的生效性依赖 Chromium 版本（作为第 4 层兜底，即使不生效也有前三层）。
- 探针页（`BlockNoteEditorScreen` / `BlockNoteProbeScreen`）各自创建 WebView，不涉及面板，
  未接入本机制；共用组件默认参数为 `false`，行为不变。

## 9. 踩坑记录：桥回调线程导致「正文一直显示正在装载…」

**症状**：进入已有灵感的编辑页，标题与字数行正常，正文区一直停在「正在装载…」。

**根因**：`ready` 分支里同步调用了 `applyImeSuppression()`（内部 `evaluateJavascript`）。
`handleUpMessage` 运行在 WebView 的 **Java 桥线程**（`@JavascriptInterface` 的既定行为），
在此线程调用 WebView 方法会抛 `IllegalStateException`；异常被 `handleUpMessage` 外层的
`catch (e: Exception)` 静默吞掉，**同一行后面的 `mainHandler.post { flushIfReady() }`
也就不再执行** → `init` 永不下发。

而 JS 侧 `booted` 只在收到 `init` 时置位（`EditorApp.tsx` 的 `case "init"` →
`setBooted(true)`），`booted === false` 时渲染 `<div className="editor-loading">正在装载…</div>`。
**装载态文案在 JS 侧，但开关在 Kotlin 侧的 init 下发**——两端各持一半，是本 bug 的迷惑点。

**修法**：

1. 止血——把注入与 `flushIfReady()` 放进同一个 `mainHandler.post { ... }`；
2. 加固——**把整条上行消息统一 post 到主线程后再解析**：`handleUpMessage` 只负责切线程，
   实际处理移到 `handleUpMessageOnMainThread`。这样"线程正确性"被收敛为入口处唯一一处约定，
   从结构上消除"某个分支忘了 post 就调 WebView 方法"的可能（这层包装被拆散过一次，
   正是本 bug 的由来）。

**教训（可复用）**：

1. `@JavascriptInterface` 方法一律运行在 Java 桥线程，回调里**任何** WebView 方法
   （`evaluateJavascript` / `loadUrl` / `setBackgroundColor` …）都必须先 post 到主线程；
2. `catch (e: Exception) { Log.e(...) }` 这种"只打日志不中断"的写法，会把**线程违规**
   这类致命错误伪装成"某个功能没生效"，排查时应先看有没有异常栈；
3. WebView 出问题时，先分清「页面内 JS 的状态」与「Kotlin 侧的状态」——
   本 bug 的 loading 文案在 JS，而触发它切换的消息来自 Kotlin。
